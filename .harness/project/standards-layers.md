# 개발 기준 계층

공통 하네스는 기준을 한 덩어리로 덮어쓰지 않습니다. 회사 공통, 스택, 템플릿, 프로젝트, 개인 기준을 계층으로 보고 충돌을 드러낸 뒤 하나의 작업 맥락으로 정리합니다.

## 계층

| 계층 | 범위 | 예시 위치 | 커밋 여부 | 역할 |
| --- | --- | --- | --- | --- |
| 회사 공통 기준 | 모든 프로젝트 공통 | `.harness/`, `CLAUDE.md`, `AGENTS.md` | 커밋 | 스택과 무관한 개발 흐름, 검증 절차, 세션 운영 기준 |
| 스택 기준 | 특정 개발 스택 | `.harness/project/stack-preset-rules.md`, 외부 stack manifest | 커밋 | 공통 흐름을 프레임워크와 런타임 조합의 기술 구조와 명령으로 해석. 제품 유형 계약은 포함하지 않음 |
| 템플릿 사용 계약 | 선택한 제품/scaffold 템플릿 | `.harness/project/template-contract.md`, 템플릿 저장소의 개발 가이드 | 커밋 | 관리자 앱 등 제품 유형과 생성 코드가 요구하는 계약을 프로젝트에 연결하고 갭을 검사 |
| 프로젝트 기준 | 현재 저장소 팀 기준 | `.harness/project/*.md`, 기존 전용 하네스 문서 | 커밋 | 도메인, 아키텍처, 릴리스, 팀 관례 |
| 개인 기준 | 개인 작업 선호 | `CLAUDE.local.md`, `.claude/settings.local.json`, 개인 로컬 방법론 파일 | 커밋하지 않음 | 개인 도구 설정과 선호. 팀 기준을 바꾸지 않음 |

## 기준이 쌓이는 순서

1. 회사 공통 기준
2. 스택 기준
3. 템플릿 사용 계약
4. 프로젝트 기준
5. 개인 기준

이 순서는 설치와 이해의 기반 순서입니다. 회사 공통 기준은 모든 기준의 바닥이지만, 구체 작업에서 항상 더 구체적인 프로젝트 기준보다 우선한다는 뜻은 아닙니다.

## 충돌 해석 순서

1. 회사 공통 필수 차단 기준
2. 사용자의 명시 지시
3. 프로젝트 기준
4. 템플릿 사용 계약
5. 스택 기준
6. 회사 공통 기본 운영 기준
7. 개인 기준
8. 에이전트 기본값

회사 공통 기준은 두 층으로 해석합니다. 보안, 권한, 검증, 복구, 기록, 차단처럼 피해를 제한하는 기준은 `회사 공통 필수 차단 기준`으로 보고 사용자 지시나 프로젝트 기준보다 앞섭니다. 반면 읽기 순서, 문서 형식, 기본 운영 절차처럼 프로젝트마다 구체화될 수 있는 기준은 `회사 공통 기본 운영 기준`으로 보고 프로젝트/템플릿/스택 기준의 해석을 따릅니다.

프로젝트 기준이 템플릿이나 스택 기준보다 앞선다는 것은 적용 프로젝트가 최종 소유권을 가진다는 뜻입니다. 템플릿이나 스택 기준과 다르게 가려면 예외 범위와 이유를 `decision-log.md`나 `waivers.json`에 남깁니다.

개인 기준은 작업 편의를 돕는 보조 기준입니다. 프로젝트 기준, 스택 기준, 회사 공통 기준을 무시하는 근거가 될 수 없습니다. 생성 컨텍스트는 기준이 아니라 보조 산출물이므로 충돌 해석 우선순위에 넣지 않습니다.

## 충돌 처리

`npm run harness:scan`은 기준 출처와 **구조적 불일치**(하네스 버전·ref, stackManifest 경로, style 값이 출처마다 다른 경우, 개인 기준 파일 감지 등)를 `.harness/session/project-scan-report.md`에 모읍니다. **문서 본문끼리의 의미적 충돌 — 스택 기준은 A라는데 프로젝트 기준은 B라고 하는 상태 — 은 자동으로 감지하지 않습니다.** 그 판단은 사람과 에이전트가 문서를 읽고 합니다(실측: 프로젝트 문서에서 스택 규칙을 뒤집어도 scan은 아무것도 표시하지 않음, 2026-08-10).

충돌이 보이면 개발자는 다음 중 하나를 선택합니다.

1. 프로젝트 기준으로 승격해 팀 공통 맥락으로 고정한다.
2. 템플릿 계약이나 스택 기준을 따르되 프로젝트 예외를 문서화한다.
3. 개인 기준을 제거하거나 개인 로컬 파일에만 남긴다.
4. 임시 예외로 허용하되 범위와 만료 조건을 `waivers.json`에 남긴다.
5. 판단을 미루고 `developer-input-queue.md`에 질문으로 남긴다.

선택 결과는 `decision-log.md`에 기록합니다.

## 하위 계층 기준을 뒤집을 때 — 재선언 관례

스택·템플릿 기준의 특정 항목을 프로젝트가 다르게 가져가는 것은 정당합니다(프로젝트가 최종 소유권). 다만 세 곳에 남겨야 안전합니다.

1. **정본**: `.harness/project/*.md`(architecture-rules 등)에 "무엇을, 스택 기준과 어떻게 다르게, 어떤 범위로" 적습니다. 표로 원 기준과 나란히 두면 명확합니다.
2. **뒤집힌 쪽에 포인터**: `stack-preset-rules.md`의 관리 섹션(`harness-stack-rules` 마커) **밖**에 "이 항목은 프로젝트 기준으로 대체됨 → 정본 링크" 한 줄을 남깁니다. 관리 섹션 안은 `stack:apply`가 덮어쓰므로 반드시 밖이어야 합니다. **이 포인터가 실질적인 안전장치입니다** — 의미적 충돌은 자동 감지되지 않으므로, 스택 문서만 읽으러 온 사람과 에이전트가 여기서 예외를 만나게 하는 것이 유일한 방어입니다.
3. **사유**: `decision-log.md`에 왜·범위·시점을 기록합니다.

재선언 실물 예시는 실습 프로젝트에 있습니다(architecture-rules의 "컴포넌트 배치 — 스택 기준 재선언" 절, 2026-08-10).

## 강제 장치

- 수동 개발자는 `npm run hooks:install`로 로컬 git hook을 선택 설치할 수 있습니다.
- 에이전트 작업은 hook 설치 여부와 무관하게 `CLAUDE.md`, 세션 boot, adapter hook을 통해 기준 확인과 완료 승인 게이트를 따라야 합니다.
- 최종화(검증·커밋·푸시) 절차는 `CLAUDE.md` 작업 원칙의 "최종화 규칙(정본)"을 따릅니다.
- 로컬 hook을 설치하면 `pre-commit`은 전체 `harness:check`, `pre-push`는 반복 검증을 줄이는 `harness:check -- --fast`를 실행합니다.
- CI나 보호 브랜치에서는 `npm run harness:check:strict`를 기준으로 차단합니다.
