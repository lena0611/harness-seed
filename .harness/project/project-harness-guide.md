# 프로젝트 하네스 작성 가이드

프로젝트 하네스는 현재 저장소의 팀이 공유해야 하는 개발 기준입니다. 공통 하네스와 스택 하네스가 제공하는 일반 기준 위에, 이 프로젝트에서만 의미 있는 도메인, 구조, 검증, 작업 절차를 쌓습니다.

## 역할

| 계층 | 담당 |
| --- | --- |
| 공통 하네스 | 모든 프로젝트가 공통으로 따를 AI 작업 흐름, 세션 복구, 문서 동기화, 검증 절차 |
| 스택 하네스 | 선택한 기술스택에서 반복되는 구조, 명령, 검증 기준 |
| 템플릿 사용 계약 | 선택한 scaffold 템플릿의 코드 묶음과 개발 가이드 사용 조건 |
| 프로젝트 하네스 | 현재 프로젝트의 도메인, 팀 관례, 아키텍처 결정, 릴리스 절차, 반복 검증 규칙 |
| 개인룰 | 개발자 개인의 도구 설정과 작업 선호 |

프로젝트 하네스는 공통/스택 기준을 덮어쓰는 별도 제품이 아닙니다. 적용된 기준을 현재 프로젝트의 실제 맥락으로 좁혀 주는 로컬 기준입니다.

## 언제 만드는가

프로젝트 하네스는 다음 상황에서 필요합니다.

- 기존 프로젝트에 회사 기준을 적용했지만 기존 팀 규칙과 도메인 지식이 흩어져 있을 때
- 스택 하네스만으로는 업무 도메인, 기존 구조, 릴리스 절차를 설명할 수 없을 때
- 버그 수정이나 기능 개발 중 같은 판단이 반복될 때
- 에이전트가 매번 코드를 다시 뒤져야 하는 프로젝트 고유 패턴이 있을 때
- 공통/스택/템플릿/개인 기준 사이에 충돌 후보가 있어 팀 기준으로 정리해야 할 때

반대로 한 번만 쓰는 임시 우회, 개인 선호, 아직 확인되지 않은 추측은 바로 프로젝트 하네스로 승격하지 않습니다.

## 작성 순서

1. 프로젝트에 맞는 스택 하네스를 먼저 설치합니다.
2. `.harness/bin/harness scan`으로 현재 구조, 스타일 설정, 기존 문서, 충돌 후보를 확인합니다.
3. `project-charter.md`와 `scope-contract.md`에 프로젝트 목적과 범위를 채웁니다.
4. 기존 README, 위키, ADR, CI, 설정 파일, 반복 코드 패턴을 확인합니다.
5. 발견한 내용을 도메인, 아키텍처, 작업 흐름, 설정 계약으로 나눕니다.
6. 충돌이 있으면 `standards-layers.md`의 우선순위로 해석하고 `decision-log.md`에 선택 이유를 남깁니다.
7. 검증 가능한 규칙은 관련 테스트, lint, build, 문서 검사, 리뷰 체크리스트와 연결합니다.
8. `.harness/bin/harness check`로 문서 링크와 기준 동기화 상태를 확인합니다.

## 파일별 책임

| 파일 | 적을 내용 |
| --- | --- |
| `project-charter.md` | 프로젝트 목적, 사용자, 성공 기준, 비목표 |
| `scope-contract.md` | 프로젝트가 다루는 범위와 명시적으로 다루지 않는 범위 |
| `local-methodology.md` | 프로젝트 하네스의 진입점과 충돌 해석 우선순위 |
| `standards-layers.md` | 공통/스택/템플릿/프로젝트/개인 기준의 계층과 충돌 처리 방식 |
| `stack-preset-rules.md` | 적용된 스택 하네스 기준. 관리 섹션은 직접 수정하지 않음 |
| `template-contract.md` | 적용된 scaffold 템플릿의 사용 계약 브리지. 전체 가이드는 템플릿 저장소가 소유 |
| `domain-rules.md` | 업무 용어, 핵심 엔티티, 도메인 불변식, 외부 시스템 계약 |
| `architecture-rules.md` | 모듈 경계, 의존 방향, 데이터 흐름, 공개 API 경계 |
| `coding-conventions.md` | 언어·런타임 제약, 금지 문법·API, 서식, 네이밍 — 도구(lint·formatter)가 못 잡는 규칙만 |
| `workflow-rules.md` | 개발, 리뷰, 릴리스, 장애 대응, 검증 명령 |
| `commit-push-rules.md` | commit/push 승인 이후 실행되는 git hook, 커밋 템플릿, 최종 안전 검사 |
| `config-contract.md` | 환경변수, 설정 파일, secret, 런타임 설정 계약 |
| `decision-log.md` | 기준 충돌, 예외, 아키텍처 변경의 선택 이유 |
| `developer-input-queue.md` | 확인이 필요한 질문과 보류된 판단 |

프로젝트 하네스에서 가장 많이 쓰는 파일은 `domain-rules.md`, `architecture-rules.md`, `coding-conventions.md`, `workflow-rules.md`입니다. 나머지는 기준을 찾고 충돌을 해석하기 위한 지지 문서입니다.

## 공통/스택 하네스와 어우러지는 원칙

- 공통 하네스의 세션, 문서, 검증 절차를 프로젝트 문서에서 다시 복사하지 않습니다.
- 스택 하네스의 관리 섹션을 직접 고치지 않습니다. 보충이나 예외는 관리 섹션 밖에 적습니다.
- 프로젝트 기준은 “우리 프로젝트에서는 왜 이렇게 하는가”를 설명합니다.
- 스택 기준과 다른 선택을 한다면 예외 범위, 이유, 검증 방법을 함께 적습니다.
- 회사 공통 안전 기준이나 사용자의 명시 지시를 프로젝트 기준으로 낮추지 않습니다.
- 개인룰은 팀 공유 기준보다 우선하지 않습니다. 반복 가치가 있으면 프로젝트 기준으로 승격합니다.
- 확신할 수 없는 내용은 규칙으로 고정하지 않고 `developer-input-queue.md`에 질문으로 남깁니다.

## 규칙 작성 형식

프로젝트 규칙은 짧아도 근거와 검증 방법을 같이 남깁니다.

```md
## <규칙 이름>

- 범위: 이 규칙이 적용되는 모듈, API, 배치, 작업 종류
- 근거: 기존 코드, 장애, 리뷰, 사용자 지시, 반복 패턴
- 기준: 앞으로 따라야 할 판단
- 검증: 확인할 명령, 테스트, 리뷰 항목, 문서
- 예외: 허용되는 예외와 기록 위치
```

이 형식을 강제 템플릿으로 쓰라는 뜻은 아닙니다. 다만 근거와 검증이 없으면 에이전트가 규칙을 맥락 없이 암기하게 되므로, 최소한 둘 중 하나는 남겨야 합니다.

## 예시

도메인 규칙:

```md
## 상태 변경 제한

- 범위: 상태 변경 API와 관련 작업 흐름
- 근거: 기존 운영 정책과 장애 대응 기록
- 기준: 종료 상태의 대상은 일반 변경 흐름에서 다시 활성화하지 않는다.
- 검증: 상태 변경 테스트와 예외 처리 경로 확인
- 예외: 운영 승인으로 복구해야 하면 별도 복구 절차와 decision-log에 사유 기록
```

아키텍처 규칙:

```md
## 외부 이벤트 재처리 안전성

- 범위: 외부 시스템 이벤트 수신과 동기화 작업
- 근거: 같은 외부 이벤트가 재전송될 수 있는 반복 패턴
- 기준: 외부 이벤트 처리에는 재처리 안전성을 확인할 수 있는 고유 키를 둔다.
- 검증: 중복 이벤트 처리 테스트와 저장 결과 확인
```

작업 흐름 규칙:

```md
## 외부 계약 필드 변경

- 범위: 외부 시스템이나 다른 저장소가 소비하는 데이터 계약
- 근거: 소비자가 같은 필드 계약을 공유해야 함
- 기준: 계약 필드를 추가, 제거, 이름 변경하면 contract 문서와 관련 테스트를 함께 갱신한다.
- 검증: 계약 테스트, 타입 검사, 문서 diff 확인
```

## 기존 프로젝트에서 만드는 방법

기존 프로젝트에서는 새 규칙을 처음부터 쓰기보다 이미 존재하는 기준을 흡수합니다.

1. `.harness/bin/harness scan`의 `.harness/session/project-scan-report.md`를 확인합니다.
2. 기존 README, 위키, ADR, 에이전트 설정, CI 설정, 운영 문서를 기준 출처로 봅니다.
3. `.editorconfig`, ESLint, Prettier, tsconfig 같은 설정은 스타일 출처로 보고 프로젝트 규칙 초안에 반영합니다.
4. 코드에서 같은 패턴이 2곳 이상 반복되면 로컬룰 후보로 기록합니다.
5. 기존 전용 하네스 문서가 있으면 삭제하지 말고 `local-methodology.md`에서 연결합니다.
6. 충돌 후보는 즉시 하나로 덮지 말고 팀 선택이 필요한 항목으로 남깁니다.

## 기존 진입점 문서(CLAUDE.md 등)의 규칙을 룰 문서로 옮기기

하네스를 깔기 전부터 자기 `CLAUDE.md`(또는 그 파일이 가리키는 규약 문서)에 규칙 본문을 두고 있던 프로젝트가 대상입니다. 설치는 그 파일 위에 하네스 블록만 얹고 내용은 건드리지 않으므로, 규칙은 여전히 진입점에 통째로 실리고 하네스 도구(`context`·`impact`·`scan`)는 그 규칙을 보지 못합니다. 개발자가 "CLAUDE.md의 규칙을 하네스 문서로 마이그레이션해줘"라고 하면 이 절차를 따릅니다. **시점은 팀이 정합니다 — 에이전트가 먼저 나서지 않습니다.**

1. **내용은 옮기지 않고 등록만 하는 것부터.** 별도 규약·셋업 문서(예: `CONVENTIONS.md`, `DEV_SETUP.md`)는 그 자리에 두고 `.harness/documentation/document-registry.local.json`의 `children`에 등록합니다. 프로젝트의 슬래시 명령(`.claude/commands/*.md`)도 같이. 이것만으로 링크 검사가 관리 대상으로 보고 작업 컨텍스트 후보에 들어갑니다.
2. **얻는 게 있는 절만 옮깁니다.** 옮기면 그 폴더를 고칠 때 검사가 규칙을 짚어주는 절이 대상입니다. 나머지는 그대로 둡니다.

   | 원문의 절 | 옮길 곳 | 얻는 것 |
   | --- | --- | --- |
   | 계층 구조·의존 방향·트랜잭션 경계 | `architecture-rules.md` | 구조 변경 시 컨텍스트가 규칙을 고름 |
   | 브랜치명·커밋 메시지 형식 | `commit-push-rules.md` + `.github/commit-template.txt` | 커밋 시점에 형식이 보임 |
   | 수정 금지 영역·실수 비용 큰 경로 | `critical-paths.md` 선언 표 | 그 경로 변경에 `impact`가 강한 리뷰를 요구 |
   | 업무 용어·불변식·금지되는 처리 | `domain-rules.md` | 도메인 작업 컨텍스트에 실림 |
   | 언어·런타임 제약, 금지 문법·API, 서식, 네이밍 | `coding-conventions.md` | 코드 작성 컨텍스트에 실림 (도구가 잡는 규칙은 도구 설정을 가리키고 옮기지 않음) |
   | 검증 명령(lint·phpcs 실행법) | `workflow-rules.md` "검증 명령" | 완료 전 검증 후보로 잡힘 |
   | 환경 셋업 절차(도구 설치 방법) | **원문에 남김** (1번 등록만) | 절차 문서라 옮겨도 검사가 더 해주는 게 없음 |

   위험 경로는 옮기기 전에 **그 경로가 저장소에 실존하는지** 확인합니다(없는 경로는 유령 선언).
   `coding-conventions.md`는 **채워지면 자동으로 항상 읽기**에 실립니다(뼈대의 `TBD`가 아닌 규칙이 한 줄이라도 있으면). 코딩 규약은 정의상 모든 코드 변경에 걸리기 때문입니다 — 따로 등록할 것이 없습니다. 서비스 하나에만 적용되는 규칙은 이 파일이 아니라 서비스 문서에 둡니다(저장소 전역으로 실리면 다른 서비스 작업에 소음).
3. **원문에는 포인터 한 줄을 남깁니다** — 절 제목은 유지하고 본문 대신 "→ `.harness/project/…`로 옮겼다(날짜)". 같은 규칙이 두 곳에 있으면 한쪽이 낡습니다.
   **모든 절을 옮겼으면 마무리로 둘을 합니다.** ① 옮긴 내용을 표로 보여줍니다 — `원문 절 | 옮긴 곳(문서·절) | 원문에 남긴 것`. 사용자가 무엇이 어디로 갔는지 한눈에 확인할 수 있어야 합니다. ② **명시적으로 묻습니다**: "원문 `<파일>`은 포인터만 남아 사실상 참조되지 않습니다. 지울까요?" (Claude는 질문 UI로, 선택지: 지움 / 포인터로 유지 / 나중에). 답을 받기 전에 지우지 않고, 답을 받기 전에 턴을 끝내지도 않습니다. 지우기로 하면 진입점(CLAUDE.md)의 그 파일 포인터도 함께 정리합니다.
4. **`CLAUDE.md` 프로젝트 영역에는 "어디를 읽어라"만** — 읽기 순서(하네스 → 규약 문서 → 셋업 문서)와 어느 절을 어디로 옮겼는지. 규칙 본문은 쓰지 않습니다.
5. **확인은 실행으로.** `harness context "<옮긴 주제로 한 문장>"`이 옮긴 룰 문서를 고르는지 · 위험 경로 아래에 임시 파일을 만들고 `harness impact`가 지목하는지(확인 후 삭제) · `node .harness/bin/doc-link-check.mjs --strict` 통과 · `harness check` 통과. 실측 없이 "옮겼다"고 보고하지 않습니다.
6. 프로젝트가 `.claude/settings.json`에 자기 허용 명령·훅을 갖고 있었다면 설치가 병합해 둡니다. 존재하지 않는 스크립트를 허용 목록에 두고 있으면 그때 정리합니다.

## 통합 저장소의 서비스 폴더 `CLAUDE.md` — 전용 규칙을 담거나, 나눈 파일의 목차로

한 저장소에 서비스가 여럿(예: `ss/multisite/`, `ss/smartclub/`)이면 하네스는 **루트에 한 벌**이고, 서비스 폴더의 `CLAUDE.md`는 그 서비스 **전용** 규칙의 자리입니다. 개발자가 "OO 폴더에 CLAUDE.md 만들어줘"라고 하면 이 요령을 따릅니다.

**전제 — 루트 내용은 되풀이하지 않습니다.** 루트 `CLAUDE.md`는 세션 시작에 이미 실려 있고(하위 폴더를 주 폴더로 열어도 도달 — 2026-09-02 실측), 하위 폴더의 `CLAUDE.md`는 그 폴더 안 파일을 다룰 때 **추가로** 실립니다. 읽기 순서·공통 규칙 위치를 다시 쓰면 같은 말이 두 번 실릴 뿐입니다. 루트가 안 실리는 유일한 경우(연결 저장소로 접근)엔 하위 `CLAUDE.md`도 안 실리므로, 되풀이가 도움이 되는 경우는 없습니다.

**두 가지 모양 — 양이 정합니다.**
- **한 파일**: 전용 규칙이 몇 개 안 되면 `ss/multisite/CLAUDE.md`에 **전부** 씁니다. 그 폴더를 건드릴 때 통째로 실리는데, 서비스 전용 규칙은 그때 다 필요한 것이라 낭비가 아닙니다.
- **유형별 파일 + 목차**: 규칙이 늘면 루트처럼 유형별로 나누고(`ss/multisite/rules/architecture.md`·`domain.md`·`coding.md` …) `CLAUDE.md`는 그 파일들의 목차만 갖습니다. 작업 컨텍스트가 요청에 맞는 파일만 고르므로 규칙이 많을수록 유리합니다. 한 파일로 시작해 나중에 나눠도 됩니다.

**공통 요령**
1. 전용 규칙이 없으면 파일을 만들지 않습니다 — 첫 규칙이 생길 때 만듭니다.
2. 저장소 공통과 겹치는 규칙은 쓰지 않고 루트 룰 문서(`.harness/project/*.md`)에 둡니다. 다른 서비스에도 적용되기 시작한 규칙은 루트로 올리고 원자리에 한 줄 포인터를 남깁니다 — 방향은 항상 서비스 → 공통.
3. **만든 파일마다** `.harness/documentation/document-registry.local.json`의 `children`에 한 줄 등록합니다. 그것으로 링크 검사·작업 컨텍스트 후보·스캔 분류가 모두 됩니다(미등록이면 orphan). 작업 컨텍스트는 등록된 프로젝트 문서 중 요청 단어를 가장 많이 담은 것에 자리를 보장합니다(최대 3칸).
4. `profile.json`의 `sources[]`에는 넣지 **않습니다** — 그 목록은 "저장소 전체가 항상 따르는 기준"용이고(`inject: "always"`면 모든 컨텍스트에 실림), 서비스 하나의 규칙을 거기 두면 다른 서비스 작업에 소음이 됩니다.

**견본 — 한 파일**

```markdown
# 멀티사이트 백엔드 (ss/multisite) 전용 규칙

## 아키텍처
- 모든 경기관제 API는 `{ ok, data, serverTime }` 봉투로 응답한다.

## 도메인
- 사이트(site) = 골프장 한 곳. 영업현황은 사이트 단위로 집계한다.
```

**견본 — 목차**

```markdown
# 멀티사이트 백엔드 (ss/multisite) 전용 규칙

- [아키텍처](rules/architecture.md) · [도메인](rules/domain.md) · [코딩](rules/coding.md)
```

**기획 문서는 서비스 이름으로** — `spec-sources.json`의 소스 id를 서비스 이름(`multisite`)으로, 매핑 경로를 그 서비스 코드(`ss/multisite/**`)로 두면 다른 서비스 개발자는 그 안내를 만나지 않습니다([spec-authority-workflow.md](./spec-authority-workflow.md) 모놀리스 절).

## 승격 기준

작업 중 발견한 내용을 프로젝트 하네스로 승격할지는 다음 기준으로 판단합니다.

| 발견한 내용 | 처리 |
| --- | --- |
| 한 번뿐인 구현 세부사항 | 코드에만 둠 |
| 같은 판단이 반복되는 도메인 규칙 | `domain-rules.md` 후보 |
| 여러 모듈에서 반복되는 구조나 의존 방향 | `architecture-rules.md` 후보 |
| 리뷰마다 반복되는 확인 항목 | `workflow-rules.md` 후보 |
| 사람이 매번 기억해야 지켜지는 런타임 불변식 | 문서보다 테스트/CI/lint 가드 우선 (누락 = 빌드 실패) |
| 설정 파일에 이미 고정된 스타일 | 스타일 규칙 초안 또는 로컬룰 |
| 팀 합의가 필요한 충돌 | `developer-input-queue.md` 후 `decision-log.md` |
| 개인 작업 편의 | 개인룰에만 둠 |

승격은 “문서가 많아 보이게 하기 위해” 하는 일이 아닙니다. 다음 작업에서 같은 실수를 줄이거나, 에이전트가 추측하지 않아도 되게 만드는 정보만 올립니다.

승격할 때는 먼저 "이 규칙은 문서로 남길 것인가, 실행 가능한 검증으로 만들 것인가"를 묻습니다. "동적 클래스는 safelist에 등록한다"처럼 어길 때 조용히 깨지고 사람이 매번 기억해야 지켜지는 규칙은 문서로는 못 막습니다 — 테스트, CI 가드, lint 규칙으로 표현해 누락이 빌드 실패로 드러나게 하고, 문서에는 그 검증의 존재와 이유만 남깁니다. 판단 기준은 [`enforcement-ladder.md`](../policy/enforcement-ladder.md)의 기본 판단 순서 0번입니다.

## 검증과 유지보수

- 프로젝트 하네스를 바꾼 뒤에는 `.harness/bin/harness check`를 실행합니다.
- 문서가 길어질 때의 분리 기준은 `.harness/documentation/split-thresholds.md`가 정본입니다.
- 룰 문서 상단에는 현재 따라야 할 요약과 적용 범위를 두고, 오래된 사례와 세부 근거는 하위 문서나 decision-log로 분리합니다.
- 에이전트가 모든 프로젝트 룰을 매번 읽는다고 가정하지 말고 `.harness/bin/harness context "<작업 설명>"`으로 판단 기준과 충돌 우선순위를 좁히게 합니다.
- 규칙을 바꾸면 관련 테스트, CI, README, 운영 문서도 함께 봅니다.
- 더 이상 맞지 않는 규칙은 삭제보다 먼저 `decision-log.md`에 변경 이유를 남깁니다.
- 임시 예외는 범위와 만료 조건을 남기고, 가능하면 `waivers.json`에 기록합니다.

## 에이전트에게 맡길 때

에이전트에게 프로젝트 하네스 보강을 맡길 때는 다음처럼 지시합니다.

```text
현재 버그 수정을 하면서 발견한 반복 도메인/구조/검증 규칙이 있으면
.harness/project/*의 적절한 파일에 로컬룰 후보로 기록해라.
확신할 수 없는 내용은 규칙으로 확정하지 말고 developer-input-queue.md에 질문으로 남겨라.
```

이 지시가 있으면 에이전트는 공통/스택 기준을 먼저 읽고, 실제 코드와 작업 결과를 근거로 프로젝트 하네스를 조금씩 성장시킵니다.
