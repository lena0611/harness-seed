# 기획 문서 매핑

기획 저장소의 문서가 이 프로젝트의 어느 코드로 구현됐는지 연결하는 표입니다.

이 문서는 **프로젝트가 소유**합니다. 기획팀은 이 파일의 존재를 알 필요가 없고, 하네스 업데이트가 덮어쓰지 않습니다.

## 왜 코드 쪽에서 관리하는가

기획 문서는 "무엇을 왜"를 담고, 코드 경로는 리팩터링마다 바뀝니다. 기획팀이 코드 경로를 관리하면 리팩터링할 때마다 기획 문서가 틀려지고, 기획팀은 그걸 고칠 수단이 없습니다. 그래서 연결고리는 코드와 함께 움직이는 이곳에 둡니다.

## 매핑 표

`기획 문서`는 기획 저장소 루트 기준 경로, `구현 경로`는 이 저장소 기준 경로입니다. 여러 경로는 쉼표로 구분합니다.

| 기획 문서 | 구현 경로 | 비고 |
| --- | --- | --- |
| TBD | TBD | 예: features/로그인.md → src/views/LoginView.vue, src/apis/auth.ts (예시라 백틱 없이 표기) |

비고에는 담당(팀/사람)을 함께 적는 것을 권장합니다(예: 담당: A팀). 담당 밖 기획 변경을 발견했을 때 전달할 곳이 즉시 정해집니다.

## 작성 기준

- **한 문서에 여러 코드 경로**는 정상입니다. 화면, API, 상태 모듈이 함께 걸립니다.
- **한 코드가 여러 문서**에 걸려도 됩니다. 공통 컴포넌트가 여러 기능에 쓰이는 경우입니다.
- 디렉터리 단위(`src/views/member/**`)로 적어도 됩니다. 페이지가 여러 파일로 나뉘면 이쪽이 관리하기 쉽습니다.
- **매핑이 없는 기획 문서**는 아직 구현되지 않았거나 연결이 누락된 것입니다. `harness:spec:status`가 알려줍니다.
- **매핑이 없는 기능 코드**는 사양 없이 구현된 영역일 수 있습니다. 검증에서 참고 정보로 표시합니다.

## 갱신 시점

- 새 기능을 구현하면서 그 기능의 기획 문서를 읽었다면, 그때 한 줄 추가합니다.
- 파일을 옮기거나 이름을 바꾸면 구현 경로를 함께 고칩니다.
- 기획 문서가 폐기되면(`archive/`로 이동) 해당 행을 지우거나 비고에 폐기를 적습니다.

## 관련

- 연결 설정: `.harness/spec-sources.json` (어느 저장소를 참조하는가)
- 기준 시점: `.harness/spec-lock.json` (어느 시점 기획을 기준으로 개발했는가)
- 명령: `npm run harness:spec:fetch` (최초 연동 기준 생성 / lock이 있으면 캐시만 갱신), `npm run harness:spec:status` (연동 상태와 미정산 확인), `npm run harness:spec:settle` (내 변경에 걸린 문서만 정산), 전체 기준 이동은 `npm run harness:spec:fetch -- --move-baseline`
- 이 표의 정합(문서가 기준에 존재하는가, 구현 경로가 실존하는가)은 커밋 검증이 확인합니다.
