# 기획 문서 연동 작업 절차 (플랫폼 중립 정본)

기획팀이 관리하는 문서 저장소를 개발 기준으로 연결하고, 작업할 때 그 기준을 따르는 절차입니다.

**이 문서가 정본입니다.** Claude Code의 `/기획문서연동`, Codex, Copilot 진입점은 모두 이 문서를 읽고 같은 절차를 수행합니다. 플랫폼별 파일은 호출 어댑터일 뿐 별도 규칙을 두지 않습니다.

## 용어 (이것만 알면 됩니다)

| 이 문서의 말 | 쉽게 말하면 | 실제로 무엇인가 |
| --- | --- | --- |
| 기준 시점, lock | **우리가 본 기획 버전** | "우리 팀은 이 시점 기획을 보고 개발했다"는 기록(`spec-lock.json`). 커밋해서 팀과 공유합니다. npm의 package-lock과 같은 자리입니다 |
| 캐시, 수화 | **기준 본문 받아오기** | 팀 기준 시점의 문서 내용을 내 PC로 내려받는 것(`generated/spec-cache/`). git에 커밋하지 않고 각자 로컬에만 둡니다(`node_modules`와 같은 취급) |
| 최신 사본 | **읽어볼 최신 본문** | 기준 이후 바뀐 문서를 확인용으로 꺼내둔 것(`generated/spec-latest/`). 여기서 읽은 것만 정산 대상이 됩니다 |
| 정산, settle | **확인 완료 표시** | "바뀐 기획을 봤고 반영했다"를 기록하는 것. **읽은 그 시점만** 기록되며, 그 뒤에 올라온 변경은 다음 확인에 다시 나옵니다 |
| drift | **어긋남** | 기획서와 코드가 서로 다른 상태 |
| 매핑, spec-map | **문서↔코드 연결표** | "이 기획서는 이 코드로 구현했다"를 적어둔 표 |

## 저장 공간 세 자리 (0.2.103)

| 위치 | 무엇 | 누가 쓰나 | 지워도 되나 |
| --- | --- | --- | --- |
| `.harness/generated/spec-cache/<source>/` | **팀 기준 본문** — lock의 사본 | 수화(`hydrate`)와 `--at-lock`만 | 예(재생성됨) |
| 캐시 저장소의 git 객체 | 최신 확인용 | `--cache-only`, freshness, push 게이트 | 예 |
| `.harness/generated/spec-latest/<source>/` + manifest | **읽어볼 최신 본문** — 정산의 근거, manifest와 정확히 같은 집합 | `--cache-only`, push 게이트 | 예(단, 정산 전이면 다시 확인 필요) |

기준 본문과 최신 본문을 한 폴더에 두면 "최신으로 받기"와 "기준으로 되돌리기"가 서로를 덮어씁니다. 자리를 나눠야 두 요구가 공존합니다.

lock을 바꾸는 명령(최초 `fetch`·`--move-baseline`·`settle`)은 끝에 기준 본문을 맞춥니다. 이때 받아오기가 실패하면 **lock은 이미 정본으로 갱신됐고 본문만 뒤처진 상태**로 남습니다 — 그 소스는 컨텍스트 주입에서 제외되고, `--at-lock`으로 다시 맞춥니다.

## 전제

- 기획팀은 코드도 하네스도 모릅니다. 자기 Git 저장소에 markdown을 쓰고 push할 뿐입니다.
- 개발자도 이 연동의 내부 명령을 몰라도 됩니다. 에이전트가 대신 수행하고 결과만 확인받습니다.
- 연결·매핑·기준 시점은 **전부 개발 저장소가 소유**합니다. 기획 저장소에는 어떤 경우에도 쓰지 않습니다.

## 1. 모든 코드 작업 시작 시 (연동된 프로젝트)

`.harness/spec-lock.json`이 있으면 **작업 크기와 무관하게** 관련 기획을 먼저 확인합니다. "간단한 수정이라 생략"하지 않습니다 — 사양이 바뀐 줄 모르고 고치는 것이 가장 비싼 실수입니다.

```bash
npm run harness:context -- "<작업 설명>"
```

이 명령이 세 가지를 함께 처리합니다.

1. 본문이 없으면 팀 기준 시점으로 받아옵니다(기준은 옮기지 않음).
2. 최신 기획을 짧게 확인합니다(비파괴).
3. 결과를 세 상태로 보여줍니다.
   - **팀 기준(lock) 문서** — 지금 우리 기준
   - **기준 이후 바뀐 문서** — 최신을 읽고 구현해야 합니다
   - **새로 올라온 문서** — 아직 기준에 없지만 이번 작업과 관련될 수 있습니다

최신 확인에 실패하면(오프라인 등) "확인하지 못함"이 표시됩니다. 그때는 팀 기준으로 진행하되, 기획이 바뀌었을 수 있음을 인지하고 작업합니다.

작업 후 처리:

- 구현한 기능의 기획 문서가 있으면 `.harness/project/spec-map.md`에 매핑 한 줄을 남깁니다.
- 바뀐 문서를 확인하고 반영했으면 `npm run harness:spec:settle`로 정산하고, `spec-lock.json` 변경을 커밋에 포함합니다.

## 2. 아직 연동되지 않은 프로젝트

`.harness/spec-sources.json`이 없고 개발자가 요구사항 기반 개발을 요청하면, **최초 1회만** 평이한 말로 묻습니다.

> 이 프로젝트의 요구사항을 관리하는 Git 저장소가 있나요? 있다면 주소를 알려주세요.

- 주소를 **추측하지 않습니다.** 관례상 있을 법한 경로를 후보로 제시하지도 않습니다.
- **없다고 하면 그 사실을 `.harness/session/decision-log.md`에 한 줄 기록하고 그대로 진행합니다.** 기록하지 않으면 다음 작업이나 다른 에이전트가 같은 질문을 반복합니다.

  ```text
  ## <날짜> - 기획 문서 연동 보류
  - 요구사항을 관리하는 별도 Git 저장소가 없다고 확인했습니다. 연동을 설정하지 않고 진행합니다.
  - 나중에 저장소가 생기면 `/기획문서연동`(또는 이 절차 2절)으로 연결합니다.
  ```

- 다음 실행 시 이 기록이 있으면 다시 묻지 않습니다. 개발자가 먼저 저장소를 언급할 때만 재개합니다.

주소를 받으면 `.harness/spec-sources.json`을 만듭니다.

```json
{
  "version": 1,
  "sources": [
    {
      "id": "planning",
      "repo": "<받은 주소>",
      "ref": "master",
      "include": ["**/*.md"],
      "exclude": ["**/README.md", "example/**", "archive/**"],
      "screenLinks": [".html"]
    }
  ]
}
```

`exclude` 기본값 근거: 폴더 안내용 README, 작성 견본, 폐기 문서는 현재 사양이 아닙니다. 브랜치가 `master`가 아니면 개발자에게 확인합니다.

`include`·`screenLinks`는 생략하면 위 값이 기본으로 적용됩니다. 화면 파일을 쓰지 않는 기획팀이면 `"screenLinks": []`로 끕니다.

## 화면은 문서가 링크로 선언합니다

기획팀과 합의한 저장 규칙입니다. **폴더 관례가 아니라 문서의 링크로 판정합니다.**

| 문서 | 규칙 |
| --- | --- |
| 관련 화면이 있는 기획 | 본문에 그 화면을 링크합니다 — `화면: [로그인 화면](./로그인.html)` |
| 정책만 다루는 기획 | 링크가 없습니다. **그대로 정상**입니다 |

경로로 판정하지 않는 이유: `features/README.md` 같은 안내 문서까지 화면 문서로 잡히고, 기획팀이 하네스 때문에 폴더 관례를 배워야 합니다. 링크는 기획자가 어차피 쓰는 마크다운이고, "이 문서에 화면이 있다"는 의도를 문서 자신이 말합니다.

- **링크한 화면이 저장소에 없으면 연동 오류**입니다. 반대로 **아무 문서도 참조하지 않는 화면 파일**도 오류입니다(떠도는 파일). 외부 URL·절대 경로는 검증 대상이 아닙니다(저장소 안의 파일만 확인할 수 있습니다).
- 링크된 화면은 `include`에 없어도 **자동으로 연동 대상**이 됩니다. `exclude`는 그대로 적용됩니다.
- **화면만 바뀌어도 그 문서 단위 전체가 바뀐 것**으로 봅니다. 정산은 문서와 화면을 **같은 검토 시점으로 함께** 기록하며, 한쪽만 전진시키는 것은 거부합니다("정책은 B, 화면은 A" 같은 혼합 기준 금지).
- 매핑 표에는 **대표 문서 한 줄만** 적습니다. 링크된 화면은 하네스가 자동으로 같은 단위에 포함합니다.

```
| features/로그인.md | src/screens/Login/** | 로그인 화면 |
| policies/인증정책.md | src/auth/**, src/api/** | 공통 인증 정책 |
```

- 에이전트 컨텍스트는 화면이 있는 기획이 선택되면 **정책 문서·화면·연결 코드·검토 시점**을 함께 제시합니다. 정책만 읽고 화면을 놓치거나 화면만 보고 정책을 놓치는 흐름을 막기 위함입니다.
- push 게이트는 문서든 화면이든 바뀌면 그 코드의 push를 막습니다.
- 기획 저장소 자체 CI에서도 같은 판정을 돌릴 수 있습니다: `node .harness/bin/spec-sync.mjs screen-check --dir <저장소 경로>`
- 한계(정직하게): 기획자가 화면 링크를 **깜빡하면** 그 문서는 정책 문서로 통과합니다. 링크가 곧 선언이므로, 화면을 만들었으면 문서에 링크하는 것이 기획팀의 약속입니다.

이어서 최초 기준을 만듭니다. 실패하면 원인을 그대로 보고합니다(대개 주소 오타, 브랜치 이름, 읽기 권한). 추측으로 다른 주소를 시도하지 않습니다.

```bash
npm run harness:spec:fetch
```

## 3. 매핑 만들기

가져온 문서는 `.harness/generated/spec-cache/<source-id>/`에 있습니다(git 추적 대상 아님).

1. 각 문서의 첫 문단으로 무엇에 대한 사양인지 파악합니다.
2. 저장소 코드 구조를 확인합니다.
3. **근거와 함께 매핑 초안을 제안**합니다.

```text
features/사이트전환.md → src/views/SiteSwitch.vue, src/store/site.js
근거: 문서의 "상단 사이트 이름을 눌러 목록" 흐름이 SiteSwitch.vue의 드롭다운과 일치하고,
현재 사이트 상태를 site.js가 보관합니다.
```

4. **확신이 없으면 추측으로 채우지 않습니다.** 후보를 제시하거나 비워 둡니다. 잘못된 매핑은 없는 매핑보다 나쁩니다.
5. 개발자가 확인한 것만 `spec-map.md`에 기록합니다. 비고에 담당(팀/사람)을 적으면 담당 밖 변경 전달이 빨라집니다.
6. **짝이 필요 없다고 판정한 것도 기록합니다**: `| (사양 없음) | src/views/shared/** | 사유 |`, `| operations/배포절차.md | (코드 없음) | 사유 |`. "아직 안 봤다"와 "봤고 불필요하다"를 구분하는 장치입니다.

매핑 누락은 검사가 강제합니다: 매핑된 영역에 추가·수정된 파일에 기록도 판정도 없으면 커밋 검증이 안내하고, `specEnforcement: "gate"` 프로젝트는 push에서 차단합니다.

## 집행 강도 — 무엇이 실제로 막히는가

과장 없이 적습니다. 아래가 현재 보장의 전부입니다.

| 설정 | 커밋 | push | 비고 |
| --- | --- | --- | --- |
| `advisory` (**기본값**) | 안내 | **막지 않음** | 연동 초기 권장. 기획이 자주 바뀌는 동안 개발이 멈추지 않습니다 |
| `gate` (옵트인) | 안내 | 미정산 기획 변경·매핑 누락이면 **차단** | 기획이 안정된 뒤 팀이 직접 올립니다 |

- **기본값은 `advisory`입니다.** 연동을 마쳐도 자동으로 `gate`가 되지 않습니다 — 초기에는 기획에 구멍이 많아 push가 자주 막히는 편이 더 해롭다는 판단입니다. 준비되면 `profile.json`에 `"specEnforcement": "gate"`를 넣고 커밋하세요.
- **git hook은 clone으로 공유되지 않습니다.** `core.hooksPath`는 로컬 설정이라 저장소를 새로 받은 사람은 각자 `npm run harness:hooks:install`을 한 번 실행해야 합니다. 미설치 상태는 커밋 검증이 감지해 안내하지만, 훅이 없으면 그 안내조차 자동으로 뜨지 않습니다(`npm run harness:check`로 확인).
- **기획 저장소에 접근하지 못하면 push는 통과합니다**(fail-open). 오프라인이나 기획 저장소 장애가 개발을 멈추게 하지 않기 위함입니다. 대신 그 push는 최신 기획을 확인하지 않은 상태이며, 게이트가 그 사실을 출력합니다.
- 따라서 이 장치는 **"최신 기획이 항상 반영됨을 보장"하지 않습니다.** 보장하는 것은: 훅이 설치되고 `gate`인 프로젝트에서, 기획 저장소에 접근할 수 있을 때, 내 코드에 매핑된 기획이 바뀌었으면 정산 없이는 push되지 않는다는 것입니다.

## 4. 이미 연동된 프로젝트의 업데이트

```bash
npm run harness:spec:fetch -- --cache-only
```

1. 기준 이동 없이 최신을 받고 변경/추가/삭제를 확인합니다.
2. **변경 문서(담당 영역)**: 매핑된 코드가 새 사양과 어긋나는지 확인 → 반영 작업 보고(구현은 승인 후) → `npm run harness:spec:settle -- --doc <경로>`.
3. **담당 밖 변경**: 대신 판정하지 않습니다. `developer-input-queue.md`에 등록하고 담당에게 전달하도록 안내합니다.
4. **추가 문서**: 매핑 후보를 제안합니다. 미구현 사양이면 미매핑으로 남기고 그렇게 보고합니다.
5. **삭제 문서**: `spec-map.md` 행을 정리하고 코드 폐기 여부를 확인한 뒤 `settle -- --doc <경로>`로 기준에서도 정리합니다.
6. 변경이 없으면 한 줄로 보고하고 끝냅니다.

## 명령 계약

**팀 기준(lock)을 움직이는 것은 `--move-baseline`과 `settle`뿐입니다.** 무인자 fetch는 최초 연동에서만 기준을 만들고, 이미 lock이 있으면 캐시만 갱신합니다.

```bash
npm run harness:spec:status                       # 오프라인 상태 확인
npm run harness:spec:fetch                        # lock 없으면 최초 기준 생성 / 있으면 캐시만(비파괴)
npm run harness:spec:fetch -- --cache-only        # 최신 확인 (기준 불변)
npm run harness:spec:fetch -- --at-lock           # 팀 기준 그대로 본문 복원
npm run harness:spec:settle                       # 확인한 문서만 기준 전진 (--doc <경로>)
npm run harness:spec:fetch -- --move-baseline [--source <id>]   # 전체/해당 소스 기준 이동
```

## 기준

- 기획 저장소는 **읽기 전용**입니다. clone/fetch만 하고 어떤 경우에도 쓰지 않습니다. 캐시는 **전체 이력**으로 받습니다 — 정산이 기준을 앞으로만 옮긴다는 것을 조상 관계로 증명하기 위해서입니다(얕게 받으면 증명할 수 없고, 증명할 수 없으면 정산이 거부됩니다).
- **정산은 앞으로만 갑니다.** 목표 시점이 현재 기준보다 과거이거나 같은 이력에 없으면 거부합니다. 기획 저장소가 force-push 등으로 이력이 갈렸다면 정산이 아니라 `--move-baseline`으로 기준을 재생성합니다.
- 기획 본문은 **git에 추적되지 않는 로컬 산출물**(`generated/` 아래)로만 둡니다. 저장소에 커밋되는 기획 관련 파일은 `spec-lock.json`과 매핑 표뿐입니다.
- `spec-lock.json`은 **커밋합니다.** "우리 팀이 어느 시점 기획을 확인했는가"를 공유하는 기록입니다.
- **정본은 lock입니다.** 기준 본문(`spec-cache/`)은 그 사본이며, 받아오기가 실패하면 lock과 어긋난 채 남습니다. 그때 그 소스의 본문은 "현재 사양"으로 쓰이지 않고 컨텍스트에서 제외되며, `--at-lock`으로 다시 맞춥니다.
- 기획 저장소에 push된 문서는 **발효된 사양**입니다. 문서와 코드가 다르면 기본 판정은 **코드 drift**이고, 문서가 틀렸다고 판단되면 직접 고치지 말고 개발자에게 보고해 기획팀과 논의하게 합니다.
- **정산은 자기 몫만.** 자기 변경에 걸린 문서만 전진시키고, 남의 영역 기준을 대신 옮기지 않습니다.
- 매핑·연동으로 확정한 판단과 "영향 없음" 근거는 `.harness/session/decision-log.md`에 남깁니다.

## 수명주기

1. **소스 하나 제거**: `spec-sources.json`에서 삭제 → `spec-lock.json`의 해당 항목 삭제 → `spec-map.md` 관련 행 정리 → 캐시는 지워도 됩니다.
2. **연동 전체 해제**: `spec-sources.json`·`spec-lock.json` 삭제 + `spec-map.md` 표 비우기 → 커밋. 이후 모든 기획 검사가 비활성화됩니다.
3. **repo/ref/include·exclude 변경**: 정합 검사가 기준 기록과의 불일치를 알립니다. 확인 후 `--move-baseline --source <id>`로 재생성합니다. repo가 바뀌면 캐시를 새 저장소로 다시 clone합니다.
4. **lock v1 → v2 승격**: 자동입니다. 읽기 경로는 v1을 해석만 하고, 다음 변경 명령이 검증 후 승격합니다. 검증 실패 시 중단하고 재생성을 안내합니다.
5. **캐시 재수화**: 보통 자동입니다(pull 직후 `post-merge` 훅, 그 외에는 컨텍스트 생성이 백스톱). 수동은 `--at-lock`.
6. **하네스 전체 uninstall**: `harness:uninstall`이 spec 계열 스크립트까지 정리합니다. 연동 기록 자체를 지우려면 1~2번을 먼저 수행합니다.
