## 2026-09-07 - 결정 109: PHP 백엔드는 스택 없이 프로젝트 룰로 — 두 번째 PHP 저장소가 트리거

- 근거: 규약 250줄의 대부분이 그 저장소 고유 이름에 묶여 있다(`getParam`·`getSqlParam`·`getRecordList`의 NULL 반환·`CWebControl::autoRun` 동적 호출·`mapi_`/`wpi_` 액션 메소드·자체 오토로더). **저장소가 하나면 옮길 곳이 없다** — 스택이 로컬룰보다 더 주는 것은 "여러 저장소가 나눠 쓰고 중앙에서 버전을 올린다" 하나뿐이고, 지금 그 하나가 값을 못 낸다.
- **트리거는 두 번째 PHP 저장소다.** 그때 겹치는 규칙만 골라 올리면 경계가 저절로 정해진다(언어 층: 7.2∩8.4 문법 금지표·언어 일반 방어 코딩·PSR 스타일 / 남는 층: 자체 프레임워크 API·저장소 구조·경로). 새 저장소가 **같은 자체 프레임워크를 재사용하는지**가 그 경계를 크게 바꾼다 — 재사용하면 규약 대부분이 올라가고, 새로 짜면 언어 층만 올라간다.
- **common 저장소도 그때 스택을 주입받는다**(사용자 명시). 즉 지금의 프로젝트 로컬룰 중 스택으로 올라간 절은 그 시점에 `stack-preset-rules.md`로 옮겨진다 — 지금 로컬룰에 쓰는 방식이 나중에 버려지는 것이 아니라 **그 절만 출처가 바뀐다.**
- 준비된 재료: 2026-09-07에 작성 가이드를 검증하려고 PHP 스택 하네스 초안을 실제로 만들어 자기 검사·설치기 회귀 8종·실제 PHP 저장소 설치까지 통과시켰다(`~/practice/php-backend-stack`, 커밋 `ce6cd56`). 트리거가 오면 처음부터 만들 필요 없다. 다만 그때의 본체 계약과 대조해 다시 검증한다.
- 일반화: **스택으로 올리는 판단은 "규칙이 좋은가"가 아니라 "저장소가 몇 개인가"다.** 좋은 규칙이어도 저장소가 하나면 그 저장소 문서가 맞는 자리다.

## 2026-09-07 - 결정 108: 본체가 관리하는 것은 harness-seed·CLI·docs뿐 — 스택과 scaffold는 누구나 만들고 운영한다
- **사용자 결정(2026-09-07)**: 본체 개념으로 관리하는 저장소는 `harness-seed`, `ai-standard-cli`, `ai-standard/docs` 셋이다. **스택 하네스와 scaffold 템플릿은 어떤 개발자라도 만들고 운영할 수 있어야 하고, 본체는 그 존재를 몰라도 된다.**
- 근거: 의존 방향이 이미 그렇게 돼 있다 — 본체는 스택 manifest의 `baseHarness`를 **강제하지 않는다**(실측: `.harness/bin`·`scripts`에서 표시와 lock 복구 fallback으로만 읽는다). 판정은 전부 스택 설치기 안에 있다. 본체가 스택을 "아는" 것은 코드가 아니라 **우리가 그 스택을 소유해서 릴리스 절차에 끌어들인 결과**다.
- **이 결정을 어기는 자리(릴리스 후 걷어낼 목록)**:
  1. `scripts/sync-version-net.mjs`가 형제 경로 둘(`../vue3-vite-pinia-router`, `../cloud-front-admin-template`)을 **이름으로 박아뒀다.** 본체 몫은 자기 `package.json` 버전과 CHANGELOG 정합까지다. 위성 ref 확인은 각 스택 저장소의 자기 검사로 옮긴다.
  2. `body-release-checklist.md` 6단계의 스택·템플릿 동반 범프 절과 **결번 목록**(스택 v0.2.26·템플릿 v0.2.25)이 본체 문서에 있다. 스택 저장소 문서로 이전한다.
  3. ⛔ 번복됨(2026-09-07, 외부 리뷰 P1·P2 — 카탈로그 `ref`는 되살렸다). 되돌린 이유: `#semver:*`는 zsh에서 glob으로 죽고, 템플릿 적용은 git ref를 요구해 자리표시자로는 실행할 수 없다. **분리는 다른 방식으로 지켰다** — 본체 릴리스가 위성을 따라 올리지 않고, 카탈로그 `ref` 갱신은 위성 소유자의 요청으로 처리하는 별건이다. 원래 항목: 두 레지스트리가 **남의 저장소 버전을 `ref`로 고정한다.** 본체가 남의 릴리스 번호를 들고 있으면 그 저장소가 태그를 내는 순간 배포된 목록이 낡는다. `ref`를 빼고 설치 명령을 최신 태그로 해석되게 하는 방향(`#semver:*` 등 — 실동작 확인 필요)을 검토한다. 카탈로그 자체는 편의 목록으로 남긴다(등록 없이도 주소만 알면 설치된다 — 2026-09-07 실측).
  4. 템플릿 manifest의 `requiredStackHarness.ref`·`range`·`minVersion`은 **아무도 검사하지 않는다**(코드는 `id`만 비교 — 실측). 고정했다고 믿게 만드는 장식이라 검사를 넣거나 뺀다.
  5. `baseHarness.exactRefRequired`를 선언한 스택·템플릿이 **없다**(실측). "아무도 켜지 않은 옵트인은 부채"(결정 101) 적용 대상.
  6. ⛔ 번복됨(2026-09-07, 외부 리뷰 P1 — **검증한 정확한 태그로 되돌렸다**). 되돌린 이유: 릴리스 시점 검증이 **그 이후에 나올 본체를 보장하지 못한다.** 스택을 v0.2.142 대상으로 검증해 릴리스한 뒤 본체가 같은 `0.2.x` 안에서 호환되지 않는 태그를 내면, 스택은 아무것도 바꾸지 않았는데 신규 설치가 검증 안 된 조합을 받는다. 릴리스마다 원격-최신-base 회귀를 돌려도 그 시점 이후는 볼 수 없어 안전장치가 되지 못했다. 임의 상한(`<0.2.150`)도 문제를 미룰 뿐이다. **다시 볼 시점은 본체가 계약 파괴에 버전 경계를 올리는 규율을 실제로 채택한 뒤다.** 이미 나간 스택 v0.2.47·템플릿 v0.2.48에 이 구멍이 살아 있어 패치로 닫았다(스택 v0.2.48·템플릿 v0.2.49). 정본은 두 작성 가이드의 `baseHarness.ref` 절이고, 운영 문서가 반대로 말하지 못하게 회귀로 잠갔다(0.2.143 3차 리뷰 P2). 원래 항목: `baseHarness.ref`를 태그 고정에서 범위 표기로 전환(사용자 요청 2026-09-07로 후보 편입). 그러면 본체 릴리스마다 위성 manifest의 숫자를 갱신할 일이 사실상 사라진다는 것이 근거였다. **실측(2026-09-07)**: `npx -y git+<본체>#semver:^0.2.140 init`이 최신 매칭 태그 v0.2.141로 정상 해석됐다 — 본체는 범위를 해석은 하므로, 되돌린 것은 능력이 아니라 정책이다.
- **대신 스택 쪽에 있어야 하는 것**: 각 스택 저장소의 자기 검사가 "내 `baseHarness`가 유효한가"를 묻는다. 본체 릴리스를 어떻게 따라갈지는 작성 가이드가 안내한다(`baseHarness.ref`는 **검증한 정확한 태그만** — 0.2.143에 확정, 위 6번 참조).
- **vue3 스택의 신분(사용자 보강 2026-09-07)**: `vue3-vite-pinia-router`는 **지금 하네스 관리자가 관리할 뿐이고 본체와는 엄연히 다른 신분**이다. 같은 사람이 둘을 맡고 있는 것은 인력 사정이지 구조상의 관계가 아니다. 그래서 본체 코드·검사·릴리스 절차는 이 스택을 **특별대우하지 않는다** — 제3자가 만든 스택과 같은 자격으로 다룬다. 본체가 이 스택에 대해 갖는 것은 카탈로그의 한 줄과 "새 스택을 만들 때 복사할 견본"이라는 안내뿐이고, 그 안내도 특정 저장소 이름이 아니라 "카탈로그의 기존 항목"으로 적혀 있다(회귀 stackAuthoringGuideSpeaksEveryRuntime이 그 느슨한 형태를 잠근다). 0.2.142 릴리스가 이 스택을 push·태그까지 함께 하는 것은 **위 목록 1·2번이 아직 안 걷힌 결과**이고, 걷어낸 뒤에는 스택 저장소가 자기 리듬으로 낸다.
- **왜 0.2.142에 안 태웠나**: 위 1·2번이 곧 **그 릴리스에서 실행할 절차 자체**다. 같은 릴리스에서 고치면 릴리스로 새 절차를 시험하는 셈이고, version-net은 그 릴리스의 ref 어긋남을 잡는 안전망이었다. 문서(가이드·배포 스택 문서)만 태웠다.

## 2026-09-07 - 결정 107: 최초 설치는 스택을 추천하지 않고 목록만 보여준다
- **현재 구조를 유지한다**(사용자 확인 2026-09-07). 설치 마무리 안내가 `standards:list`를 가리키고, 그 명령이 배포된 카탈로그를 그대로 출력한다(이름·설명·주소·기준 태그·설치 명령·적용 명령). 프로젝트에 맞춰주지 않는다. 스택 미적용은 조용한 정상 상태로 남는다.
- 근거: 카탈로그가 한 개인 동안 맞출 게 없다. 추천 장치는 기존 장치를 대체하지 않고 얹기만 한다(다이어트 기준: 대체하면 도입, 얹기만 하면 안 함).
- **이미 덮여 있는 구멍**: 잘못된 스택을 고른 순간은 그 스택 설치기가 파일을 쓰기 전에 막고 카탈로그에서 호환 후보를 추천한다(`findRecommendedStackHarnesses`). 비어 있는 것은 "처음 설치할 때 무엇을 고를까" 하나뿐이다.
- **다시 볼 시점: 런타임이 다른 두 번째 스택이 카탈로그에 들어올 때**(PHP가 유력). 그때 넣을 것 — ① 카탈로그 항목마다 **거친** 판별 신호(`fits`: 의존성 선언 파일 + 표지 이름 + 배제 이름). 버전·major 판정은 넣지 않는다: 카탈로그는 "볼 만한가"에만 답하고 "호환되나"는 스택 설치기가 답한다 — 이 역할 분담이 정본 두 벌의 어긋남을 막는다. ② 프로젝트 뿌리의 의존성 선언 파일만 읽어 맞춘다(네트워크·토큰 0 — 후보 manifest 원격 조회는 비공개 저장소 권한 때문에 쓰지 않는다. 스캔의 `detectManifestFiles()`가 이미 같은 목록을 감지한다). ③ 출력은 후보 0이면 침묵, 1이면 한 줄+설치 명령, 2+면 한 줄+목록 비교 안내. 문구는 "맞을 수 있습니다"(단정 금지). ④ 맞추는 함수 하나를 설치기와 목록 명령이 공유한다(둘 다 이미 같은 카탈로그 파일을 읽는다).
- **만들지 않을 것**: 대화형 마법사, 자동 설치, 카탈로그에서의 버전 판정. 하네스는 길라잡이지 감독관이 아니다.

## 2026-09-07 - 결정 106: 자산 종류마다 GitLab 그룹을 나눈다 (harnesses / stacks / scaffolds)
- **`ai-standard/harnesses` = 공통 하네스 본체만, `ai-standard/stacks` = 스택 하네스, `ai-standard/scaffolds` = 제품 scaffold 템플릿.** 사용자 결정(2026-09-07)으로 `vue3-vite-pinia-router`를 harnesses→stacks, `cloud-front-admin-template`을 stacks→scaffolds로 이전했다.
- 근거: 이름이 역할과 어긋나 있었다 — 스택 하네스가 본체와 같은 그룹에 있어 "스택 기준을 어디서 찾나"가 그룹 이름으로 안 드러났고, `stacks`라는 이름이 실제로는 템플릿을 담고 있어 기술 스택과 제품 템플릿을 나눈 기존 결정(2026-07-10)이 저장소 배치에서는 반대로 보였다.
- 안전한 순서: **이전이 먼저, 주소 수정이 나중.** GitLab은 옛 경로를 새 경로로 넘겨주지만 반대는 없다 — 옮기기 전에 본체를 새 주소로 고치면 설치가 404가 된다. 이 순서 때문에 이전 확인(옛·새 주소 4개 `git ls-remote`) 전에는 주소를 하나도 바꾸지 않았다.
- 권한 메모: 프로젝트 이전은 GitLab **Owner** 전용이다. 하네스 관리자는 `ai-standard`의 Maintainer라 Settings → Advanced에 Transfer 절이 아예 보이지 않았고(Archive·Delete도 동일), Owner에게 부탁해 진행했다. 다음에 그룹을 손볼 때도 같은 벽을 만난다.
- GitLab 함정: 그룹의 **이름과 경로는 별개다.** 서브그룹 이름을 `scaffolds`로 바꿔도 경로는 `scaffold`로 남는다. 코드·URL·API 조회가 쓰는 것은 경로이므로 판단 기준은 항상 `path`/`full_path`다.

## 2026-09-09 — git 훅 자리를 브랜치 무관 래퍼(.git/hooks)로 (0.2.146, common #28)

- **결정**: `core.hooksPath=.githooks`(브랜치 소속 폴더)를 버리고, `core.hooksPath`를 해제한 채 git 기본 훅 폴더(`<공통 .git>/hooks`)에 하네스 래퍼를 둔다. 래퍼는 현재 브랜치의 `.githooks/<훅>`에 위임하고, 없으면 이전 훅 체인만 돌린 뒤 pre-commit·pre-push에서 한 줄 알리고 통과한다(fail-open). 판정 정본은 `hooks-state.mjs`(installed/legacy/off/optout/nogit), 예전 방식은 세션 시작이 자동 갱신.
- **왜**: 하네스 없는 브랜치로 checkout하면 `.githooks/`가 사라져 git이 아무 말 없이 훅을 건너뛰었다(PHP 백엔드, 사흘간 훅 0개). 도입기(일부 브랜치에만 하네스)에 정확히 걸리는 구멍이고, 세션 시작 자동 복구는 그 브랜치에 세션 훅 자체가 없어 못 돕는다.
- **부수 효과**: 래퍼 자리의 프로젝트 훅(`.git/hooks/pre-commit` 등)은 `harness-prev/`로 옮겨 체인 — 예전 방식이 조용히 죽이던 다른 이름의 훅(#14 commit-msg)도 이제 계속 실행된다. 워크트리도 공통 .git이라 하나.
- **외부 리뷰 반영(같은 날)**: 보관함 값 `.git/hooks/harness-prev`의 `.git/` 접두는 "공통 .git 기준"이라는 약속(해석은 `resolveHooksPath` 한 곳) · 같은 이름 재등장 시 **최신이 실행 자리**(옛 것 `.old`) · 래퍼 재진입은 **같은 저장소의 같은 훅 이름**에만 보관 원본만 실행(옛 안내 호환, 순환 없음; 다른 훅 호출은 정상 실행) · 래퍼 이름은 클라이언트 훅 전부 · 전역 `core.hooksPath`는 로컬에 **절대 경로** 명시로 덮되 전역은 불변(기록 키 `harness.hooksPathOverride`) · core.hooksPath 해석은 git 의미, `.git/` 공통 규약은 보관함 값에만.
- **대안과 기각**: `.githooks/post-checkout`으로 경고 — checkout 뒤엔 그 훅 파일도 사라져 실행 안 됨. hooksPath를 별도 절대경로 폴더로 — 워크트리·저장소 이동 시 깨지고 `.git/hooks`의 다른 이름 훅 문제는 그대로.
