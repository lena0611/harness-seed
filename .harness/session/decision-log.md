## 2026-08-18 - spec-sync 표면 4종을 공개 계약으로 승격
- 결정 83: **내부 구현이 소비자 의존을 얻으면 그 순간부터 공개 계약이다.** 멀티사이트 spec-issues-sync.mjs(소비자 소유 CI 스크립트)의 실사용 표면을 회귀(specSyncPublicSurfaceStaysLocked)로 잠금: `sha256Text`·`normalizeScreenLinks`(기본 확장자 폴백)·`buildScreenIndex`(unitFor 접기)·`readSpecState`+`pendingSettlements`({source,file,kind})·`status --json`(configured/valid/sources)·import 안전성(CLI 가드). 바꿔야 하면 테스트를 깨뜨린 커밋이 소비자 마이그레이션을 함께 안내한다.

## 2026-08-13 - 범용 안내는 project-owned 문서에 승격하지 않는다 (0.2.122)
- 결정 81: **승격 위치를 정할 때 소유 계층(managed / project-owned / marker-managed)을 먼저 판정한다.** project-owned 문서는 기존 소비자에게 업데이트로 전파되지 않는다(신규 설치만 수령) — 범용 안내를 거기 두면 "문서로 승격했다"는 공지가 기존 소비자에게 거짓이 된다. 실증: 0.2.121이 husky 공존 안내를 commit-push-rules.md(project-owned)에 넣고 공지가 "상세는 commit-push-rules.md"로 나갔는데, 기존 소비자는 업데이트를 받아도 그 절이 없고, managed인 day-0 체크리스트의 포인터는 깨진 참조가 됐다. 0.2.122에서 본문을 hook-coexistence.md(managed)로 이동, project-owned 쪽은 포인터로 축소(정본 하나 유지). 이 함정은 사전에 식별돼 세션 메모리에 기록돼 있었으나 구현 세션이 원안대로 진행 — 위치 판정은 메모리가 아니라 이 결정으로 잠근다.
- 결정 80: **같은 단어를 두 축에 쓰지 않는다** — "미정산"은 "읽었지만 정산 안 함"(spec-latest manifest 축) 전용. 원격 확인(freshness) 축은 "기준 이후 원격 변경 — 확인 전"으로 말한다. 멀티사이트 실증: 두 축이 같은 어휘를 쓰자 소비자 에이전트가 "정산 대기 없음"+"감지 2건"을 모순(병렬 실행 버그)으로 의심. 결정 45 계열(도구가 아는 것만 말한다)의 어휘 버전. 같은 뿌리로: broadcast의 무음은 "확인했고 변경 없음"만 뜻해야 하므로 확인 기록이 아예 없으면 안내를 발송하고(최초 연동도 확인 기록을 남겨 연동 직후 무음은 유지), status 감지 건수는 broadcast와 접기 단위(결정 79)를 공유한다.
- **레지스트리 유령 ref 사고 (0.2.118~120)**: 세 릴리스가 커밋 메시지로는 스택/템플릿 동반 범프를 선언했지만 **실제 스택·템플릿 저장소 릴리스가 세 번 모두 누락** — 레지스트리가 존재하지 않는 태그(스택 v0.2.24~26, 템플릿 v0.2.23~25)를 가리켰고 스택 manifest baseHarness는 v0.2.117에 정지. 발견 경로: 0.2.121 배포 중 version-net mismatch → 양쪽 원격 ls-remote 실측. **실번호 재개**(사용자 결정): 스택 v0.2.24·템플릿 v0.2.23을 실제 릴리스하고 레지스트리를 실물로 정정, 유령 번호는 결번(낡은 시드 태그로 설치하면 시끄럽게 실패 — 유령을 다른 내용으로 채워 조용히 어긋나는 것보다 낫다). 실소비자 피해 없음(멀티사이트 미적용). 교훈: 커밋 메시지의 "동반 범프"는 선언이지 증명이 아니다 — 배포 마지막에 `release:version-net`(스택 manifest 대조)을 다시 돌리는 체크리스트 6단계가 이번에 사고를 잡은 실제 장치였고, 태그 실존까지는 못 본다(레지스트리 ref의 원격 태그 실존 대조는 네트워크 검사라 회귀로 못 잠금 — 배포 절차에서 ls-remote 확인).

## 2026-08-07 - 캐시 역할 분리 (0.2.103, 0.2.102 미배포 흡수)
- 발견(자체 적대적 검토 + 외부 리뷰): 캐시 폴더 하나에 "팀 기준 본문"과 "최신 기획 본문"이라는 **다른 두 상태**를 담은 것이 아키텍처 결함이었다. `--cache-only`와 자동 수화가 같은 자리를 반대로 덮어써서, 최신 확인 후 settle이 "변경 없음"으로 끝나고 기준이 전진하지 않았다(실증). 게이트 모드에서는 차단→정산→다시 차단 무한 루프.
- 결정 31 (세 자리 분리): spec-cache(기준 전용, 수화·at-lock만 씀) / 캐시 git 객체(최신 확인, checkout 없음) / spec-latest+manifest(읽어볼 최신). 불변식: **lock을 바꾸는 모든 명령 뒤에 캐시는 lock과 일치한다**(fetch 최초·move-baseline·settle 뒤 수화).
- 결정 32 (정산 = 읽은 스냅샷): settle을 "실행 시점 원격 최신"으로 만들면 검토 후 올라온 커밋까지 확인 완료가 된다 — 내가 세운 첫 수정안의 치명적 결함이었고 리뷰가 잡았다. settle은 네트워크를 쓰지 않고 manifest의 commit/sha만 기록한다. 읽지 않은 문서는 거부, 손편집 본문은 중단, 원격이 그 사이 전진하면 다음 확인에 새 미정산으로 남는다.
- 결정 33 (경로 안전 전 구간): 삭제 경로에만 containment가 있고 쓰기 경로에 없어, 기획 저장소의 심볼릭 링크 하나로 커밋된 spec-lock이 파괴되며 "성공"으로 보고됐다. 절대경로/../빈 segment/NUL 거부 + 루트~부모 각 구성요소 lstat(중간 디렉터리 링크 차단) + 읽기 regular-file-only + 쓰기 전 링크 제거. spec-latest에도 동일 적용.
- 결정 34 (미정산의 단일 출처 = manifest): 캐시가 항상 기준과 일치하게 되면서 "캐시 vs lock" 비교는 의미를 잃었다. status·커밋 advisory의 미정산은 읽은 스냅샷 기준으로 계산하고, "기준 본문 준비 상태"는 별도 축으로 보고한다.
- 결정 35 (소스별 독립·TTL 지문·본문 관련성): 소스 하나의 장애가 전체 결과를 폐기하던 것을 소스별 상태로 분리. TTL 재사용은 선언+기준+소스집합+스키마 지문이 같을 때만, 재사용분은 "이번 실행 아님"으로 표시. 신규·변경 문서 관련성은 최신 blob 발췌까지 검색하고, 판단 불가는 숨기지 않고 "미판정"으로 노출.

### 보완 재리뷰 반영 (같은 날, 승인 조건 P1 4건 + P2 5건 전부 수용)
- 결정 41 (정산 근거는 git 객체): 종전 검증은 "manifest의 sha == 디스크 본문의 sha"뿐이라 **둘을 함께 고치면 통과**했다. 로컬 파일끼리의 대조는 provenance가 아니다. 이제 ① manifest의 소스 정체성(repo/ref)이 현재 선언·기준과 같은지 ② 스냅샷 commit이 로컬 기획 이력에 실재하는지 ③ 본문 sha가 그 commit의 내용과 같은지 ④ 삭제 표시는 그 commit의 selector 결과에 정말 없는지를 모두 확인한다. 특히 ④가 없으면 `deleted: true` 한 줄로 살아 있는 문서를 팀 기준에서 지울 수 있었다. **검증 → 계획 → 적용** 2단계로 나눠, 한 건이라도 거부되면 lock은 1바이트도 바뀌지 않는다(종전에는 루프 중 lock 객체를 직접 변형했다).
- 결정 42 (containment는 보호 루트 자신부터): `path.resolve`는 심볼릭 링크를 해소하지 않으므로, 보호 루트(`spec-cache/<id>`, `spec-latest/<id>`)가 링크면 자식 검사가 전부 무의미했다. generated 실제 루트를 확정하고 루트~leaf를 같은 규칙으로 검사한다. **읽기도 같은 API를 쓴다** — 컨텍스트 생성이 `path.join`+`readFileSync`로 읽어 "쓰기는 막고 읽기는 뚫리는" 비대칭이 있었다. 쓰기는 임시 파일+rename으로 바꿔 검사~쓰기 사이 교체도 막고 부분 기록도 없앴다(종전의 "기존 링크 제거" 코드는 도달 불가였다).
- 결정 43 (핵심 상태 손상은 미연동이 아니다): `spec-sources.json`/`spec-lock.json`/최신 확인 기록이 깨지면 종전에는 빈 값 fallback이라 각각 "연동 안 함"·"기준 없음"·"미정산 없음"으로 보였다 — 손상이 조용한 무력화로 바뀌는 fail-open이다. `{exists, valid, ...}`로 부재와 손상을 구분하고, 손상은 명시적 실패나 강한 경고로 올린다(집행 사다리는 그대로: advisory는 안내, gate는 차단).
- 결정 44 (최신 사본은 manifest의 정확한 집합): 파일을 지우지 않아 "도구는 삭제됐다는데 폴더에는 옛 본문이 있는" 상태가 됐다 — 안내받은 폴더를 연 사람은 그것을 현행 사양으로 읽는다. 매 확인마다 새 디렉터리를 완성한 뒤 교체하고, 정산으로 소비된 스냅샷은 기록과 파일을 함께 지운다.
- 결정 45 (계약을 구현보다 세게 쓰지 않는다): "캐시는 항상 lock과 일치"는 수화 실패 시 성립하지 않는다. **정본은 lock이고 캐시는 사본**이며, 실패하면 어긋난 채 남고 그 소스는 컨텍스트에서 제외된다 — 문서를 구현 쪽으로 내렸다. 같은 이유로 컨텍스트 예산은 남은 시간이 0이면 단계를 건너뛴다(최소 1초를 다시 주면 "합계 8초"가 지켜지지 않았다).
- 교훈: 이번 P1 4건은 모두 "검사는 있는데 검사의 근거가 위조 가능"하거나 "한쪽 방향에만 적용"된 유형이었다. 검사를 추가할 때 **그 검사가 신뢰하는 입력을 누가 쓸 수 있는지**를 먼저 적을 것.

### 3차 보완 재리뷰 반영 (같은 날, P1 2건 + P2 4건 + P3)
- 결정 46 (lock schema fail-closed): **JSON으로 읽히는 것과 기준으로 쓸 수 있는 것은 다르다.** `normalizeLock`이 형태가 어긋난 문서 항목을 조용히 버리는 관용이 게이트 우회가 됐다 — `{"sha": 123}` 한 곳만 망가뜨리면 그 문서가 기준에서 사라지고, push 게이트는 "기준에 없는 문서"라 drift 검사를 건너뛴다. 공용 `validateLockSchema`로 **항목 하나라도 어긋나면 lock 전체를 invalid** 처리하고 status/doc-link/settle/push tip이 공유한다. 관용은 입력 검증에서 미덕이 아니다.
- 결정 47 (정산은 앞으로만 간다 + 캐시는 전체 이력): baseSha CAS는 "읽은 뒤 기준이 움직였는가"만 본다. 실재하는 **옛 commit**의 본문·sha로 스냅샷을 갈아끼우면 provenance도 CAS도 통과하며 기준이 후퇴한다. 조상 관계로 막으려 했으나 **`--depth 1` 캐시에서는 증명 자체가 불가능**했다(실측: 첫 구현이 그대로 통과). commit 시각 휴리스틱도 같은 초 커밋에서 무너졌다. 근본 원인인 얕은 클론을 없앴다 — 기획 저장소는 markdown뿐이라 전체 이력이 작고, 그 대가로 "전진만 허용"이 추측이 아니라 **보장**이 된다. 증명 불가('unknown')는 허용이 아니라 거부이며, 옛 얕은 캐시는 다음 최신 확인에서 `--unshallow`로 치유된다. 함께: 스냅샷 commit == 그 확인의 commit, 캐시 origin == 선언 repo.
- 결정 48 (정산 전 선언↔기준 정합): 선언 ref만 바꾼 뒤 정산하면 문서 commit은 새 ref인데 소스 메타데이터는 옛 ref로 남는 혼합 lock이 만들어지고 push에서야 막혔다. settle 시작에서 `findDeclarationLockIssues`를 돌려 lock 변경 전에 중단한다.
- 결정 49 (v1 승격도 검증 뒤에): 승격 write가 정산 검증보다 앞서 있어 "한 건이라도 거부되면 lock 불변"이 거짓이었다. 승격은 거부 경로에서 절대 쓰지 않고, 정산할 것이 없어 실패할 검증도 없는 경로에서만 확정한다.
- 그 외: lock만 남고 선언이 사라진 상태를 doc-link가 명시적 정합 오류로 보고(종전에는 `declared=false`로 조용히 통과), 컨텍스트의 `(전체)` 전역 실패를 실제 소스 id 전체로 확장(그대로 두면 후보 제외 비교에 걸리지 않아 상태를 못 읽는데도 본문이 주입됨), 최신 사본 manifest를 소스별 교체 직후 기록해 중단 시 어긋남을 그 소스 하나로 제한.
- 결정 50 (화면은 문서가 링크로 선언한다, 사용자 재설계): 처음에는 경로 관례(`features/` 아래 같은 이름의 MD+HTML 쌍)로 구현했으나, 사용자가 **"MD에 관련 화면 링크가 있으면 되지 않느냐"**로 재설계했고 그쪽이 옳다. 경로 판정은 `features/README.md` 같은 안내 문서까지 화면으로 잡고(실측: 기본 exclude가 비어 있으면 그대로 실패), 기존 연동 프로젝트를 소급해 깨뜨리며, 기획팀에게 하네스 때문에 폴더 관례를 배우게 한다. **링크는 기획자가 어차피 쓰는 마크다운이고, "이 문서에 화면이 있다"는 의도를 문서 자신이 말한다** — "기획팀은 하네스를 모른다"는 창립 전제와 맞는다. 강제 세 가지: ① **링크 무결성** — 링크한 화면이 없거나 아무도 참조하지 않는 화면 파일이 있으면 기준으로 받지 않는다(연동 전 구간 fail-closed, 기획 저장소 CI용 `screen-check` 독립 명령). ② **원자성** — 화면만 바뀌어도 문서 단위 전체가 변경이고, 정산은 같은 commit으로 함께 기록한다(부분 정산 거부). ③ **대표 매핑** — 매핑 표는 대표 문서 한 줄이면 되고 링크된 화면은 하네스가 포함한다.
- 결정 51 (링크 판정의 한계를 정직하게): 기획자가 화면 링크를 깜빡하면 그 문서는 정책 문서로 통과한다 — 경로 관례가 잡던 것을 잃는다. 대신 반대 방향(링크 깨짐·떠도는 화면)은 확실히 잡고, 무엇보다 **오탐이 없다**. 판정 불가 상태(본문을 아직 못 읽음)에서는 떠도는 화면 판정을 하지 않는다 — 수화 전 상태에서 멀쩡한 화면이 고아로 잡히던 것을 실측하고 고쳤다. 적용 범위는 `spec-sources.json`의 `screenLinks`(기본 `[".html"]`, `[]`로 해제)로 선언하고 lock에도 기록해 드리프트를 검사한다.
- 이 재설계로 앞서 발견한 두 문제가 함께 사라졌다: `features/README.md`가 짝을 요구받던 것, 기존 연동 프로젝트가 업데이트만으로 깨지던 것. 현재 `planning-example`·`multisite` 저장소 그대로 월요일 연동이 가능하다.
### 4차 보완 재리뷰 반영 (같은 날, P1 3건 + P2 3건 — P1-1은 대상 소멸)
- 판정 정정: 리뷰의 P1-1(`feature/` 단수형으로 통일)은 **수용하지 않는다.** ① 그 리뷰는 경로 관례 버전을 본 것이고 지금은 링크 기반이라 폴더명이 판정에 쓰이지 않는다. ② 실제 저장소가 `features/`임을 확인하고 사용자가 "features/가 맞아"로 확정했다. 리뷰 의견이 사용자 확정 사항과 충돌하면 사용자 결정을 따른다.
- 결정 52 (집행 강도는 팀이 올린다, 사용자 결정): 연동 완료 시 `gate` 자동 활성화는 **하지 않는다** — "초반에는 기획에 구멍이 많아 push가 자주 막힐 것"이라는 사용자 판단. 기본은 advisory이고 기획이 안정된 뒤 팀이 직접 올린다. 대신 **문서에서 과장하지 않는다**: 무엇이 실제로 막히는지 표로 적고, 기본값·훅 미공유·네트워크 fail-open 세 조건을 명시했다. "항상 반영 보장"이라고 쓰지 않는다.
- 결정 53 (훅 미설치 감지): `core.hooksPath`는 clone으로 공유되지 않아 "한 명이 설치하면 팀이 검사받는다"가 성립하지 않는다. 커밋 검증이 미설치를 감지해 설치 명령을 안내한다(차단은 하지 않음 — 훅이 없으면 애초에 그 검증도 안 돈다는 한계를 문서에 적었다). CI 강제는 이번 범위에서 제외(사용자 결정).
- 결정 54 (정상 형식 self-disable 차단): 파일 삭제만 막았지 **내용 비우기**는 못 막았다 — 매핑 행을 지우면 scope가 0이 되고, lock의 files에서 항목만 빼면 그 문서가 검사에서 사라졌다(둘 다 schema 정상). push scope를 base∪tip 매핑으로 잡아 행을 지운 그 push에도 옛 매핑이 적용되게 하고, 매핑된 문서가 기준에 없으면 차단하며, 매핑은 있는데 기준이 비면 정합 오류로 올린다.
- 결정 55 (전진성 검사는 lock에 없는 문서에도): `lockedCommit`이 null이면 방향 판정이 'same'이 되어 검사가 통째로 건너뛰어졌다 — **과거에 있다가 지워진 문서를 옛 commit에서 "신규"로 되살릴 수** 있었다. 기준이 없으면 소스의 기준 commit과 비교한다.
- 결정 56 (링크 안 된 화면도 드러낸다): 떠도는 화면 판정을 선택된 집합에서만 하면 `include: ["**/*.md"]` 프로젝트에서는 링크되지 않은 화면이 선택조차 안 돼 영영 안 보였다. 저장소 전체의 화면 확장자 파일(exclude 적용)을 후보로 본다 — 링크 기반으로 바꾸며 잃었던 "링크 깜빡함" 검출을 상당 부분 되찾는다.
- 결정 57 (기록을 디렉터리 안으로): 최신 사본 기록을 디렉터리 밖에 따로 쓰면 그 사이에 죽었을 때 "새 본문 + 옛 기록"이 남아 "정확히 같은 집합"이 정상 완료 경로에서만 참이었다. 소스별 기록을 `spec-latest/<source>/.manifest.json`으로 옮겨 **rename 한 번으로 본문과 기록을 함께 확정**한다. 전역 파일은 없앴고 읽기는 소스별에서 취합한다.
- 결정 58 (self-disable 차단이 정규 흐름을 막지 않게, 자체 검토): 매핑 행 제거를 조건 없이 막았더니 **기획 폐기 → 삭제 정산 → 매핑 정리**라는 정상 절차가 push에서 걸렸다. 내가 만든 회귀다. 기준에 아직 살아 있는 사양의 매핑을 지울 때만 막고, 이미 기준에서 사라진 문서의 행 정리는 통과시킨다. 교훈: 우회 차단을 넣을 때 **그 동작을 정당하게 하는 흐름이 무엇인지** 먼저 적을 것.
- 결정 59 (새 브랜치도 base가 있다): 새 ref는 base를 비워 두었더니 브랜치를 새로 만들어 매핑을 지우는 것만으로 합집합 방어가 꺼졌다. 원격이 이미 가진 커밋 중 이 브랜치의 조상(merge-base)을 base로 삼는다.
- 결정 60 (정리도 exact-set을 지킨다): 최신 사본 정리 중 본문을 못 읽으면 건너뛰기만 해서 "기록에는 있는데 파일은 없는" 상태가 다시 생겼다. 읽지 못한 항목은 기록에서도 뺀다.
- **범위 동결(사용자 결정)**: 여기까지가 0.2.103이다. 비매핑 문서의 lock 의미 검증(문서가 링크한 화면이 기준에 없거나 다른 commit인 상태를 status/doc-link/게이트가 공유)은 **0.2.104 백로그**로 넘긴다 — 현재는 매핑된 문서에 대해서만 검증하고, 컨텍스트는 시점이 다르면 경고한다.
- 컨텍스트 정직성: 문서와 화면의 기준 commit이 다르면 "같은 시점의 검토본"이라고 말하지 않고 각각의 시점과 경고를 표시한다(혼합 lock을 한 시점으로 믿게 하면 안 된다).
- 정정: **결정 31의 "lock을 바꾸는 모든 명령 뒤에 캐시는 lock과 일치한다"는 결정 45가 대체한다** — 수화 실패 시 어긋난 채 남고 그 소스는 컨텍스트에서 제외된다. **결정 33의 "쓰기 전 링크 제거"는 결정 42가 대체한다** — 임시 파일+rename으로 교체하며, 검사~쓰기 사이 교체도 따라가지 않는다.

## 2026-08-06 - 본문 자동 수화와 업그레이드 노이즈 정리 (0.2.102, 미배포 — 0.2.103에 흡수)
- 발견(사용자 질문 연쇄): "개발자 B가 pull 받으면 기획문서가 로컬에 있냐" → **없다**. 본문은 git 미추적이라 pull로 안 온다. 더 나쁜 건 그 상태에서 컨텍스트가 "매칭되는 기획 문서를 찾지 못했습니다"라고 표시해 **"아직 안 받음"이 "기획서 없음"으로 읽히는** 것이었다(실측 확인). 에이전트가 사양 없이 작업을 시작하는 경로다.
> 아래 결정 20~30은 이후 0.2.103에서 다시 수정됐다. **최종 형태는 위의 결정 31~45다** — 20의 "커밋 검증 백스톱"은 안내만으로 축소, 22의 면제 근거는 좁은 optional 열거(단 spec-map은 연동 중이면 필수, 결정 39), 23의 비차단 표면화는 fail-closed로 승격, 21·30의 "판정 중 쓰기 제거"는 **더 이상 사실이 아니다** — 게이트는 차단 시 읽어볼 본문을 `spec-latest`에 꺼내고 그 스냅샷이 이후 정산의 근거가 된다(결정 31·32). 판정 입력은 여전히 push tip snapshot이며 tracked 파일은 건드리지 않는다.

- 결정 20 (자동 수화, 이중 경로): pull 훅(`post-merge`)이 평소 경로를 맡고, 컨텍스트 생성·커밋 검증이 백스톱이다. 훅만 두면 rebase pull과 훅 미설치자가 새고, 백스톱만 두면 에이전트를 안 쓰는 사람이 늦게 안다. 어제 게이트에서 쓴 "빠른 알림은 훅, 최종 보장은 다른 층" 패턴과 같다. 수화는 lock 기준 고정(--at-lock 의미)이고 실패는 무해하다 — pull/커밋/작업 중 무엇도 막지 않는다. 처음엔 pull 훅에 반대했다가(네트워크·rebase 미동작) 러버덕 관점에서 재검토: "pull하면 최신이 된다"는 개발자 직관에 기획 문서를 포함시키는 편이 낫고, 반대 근거 대부분은 lock 비교로 즉시 종료·조용한 실패로 해소된다.
- 결정 21 (막을 때는 읽을 수 있게): 게이트가 차단하면서 캐시에 없는 파일 경로만 알려주던 것을 고쳤다 — 이미 fetch한 객체에서 본문을 캐시에 쓴 뒤 경로를 안내한다(추가 네트워크 0). 메시지도 하네스 용어를 걷어내고 "무슨 일인가요 → 이렇게 하면 됩니다" 순서로 재작성. 하네스를 모르는 개발자가 첫 차단을 만나는 순간이 신뢰의 분기점이라는 판단.
- 결정 22 (프로젝트 소유 문서는 없어도 정상): `spec-map.md`처럼 프로젝트가 지울 수 있는 문서를 본체 레지스트리가 필수처럼 잡아, 삭제한 프로젝트에서 registry-missing + broken-link가 매 커밋 반복됐다(구버전→0.2.101 업그레이드 실측). 매니페스트의 `projectOwnedFiles`를 근거로 부재를 정상 처리한다. managed 문서 삭제는 계속 검출(면제 과확대 방지 회귀 포함).

- 결정 11 (발견망): 게이트는 "만진 코드의 사양 변경"만 본다. 신규 문서(아직 매핑 없음)와 남의 미정산 변경은 spec:status에 잔류하는 것 + CI 스케줄 백스톱(cache-only fetch → status → 매터모스트 webhook, 스킬 6절 견본)이 맡는다. CI 워크스페이스는 폐기되므로 fetch가 lock을 써도 안 샌다. MR 서버 머지가 로컬 push 훅을 우회하는 것도 이 백스톱이 커버한다.
- 미연동 프로젝트 무영향(결정 5의 게이트 적용): pre-push 훅이 spec-lock.json 존재를 셸에서 확인하고 없으면 게이트 스크립트를 실행 자체를 하지 않는다. 사용자 지시로 명시 검증(회귀: 미연동 출력 0바이트).
- 구현 중 잡은 견고성 2건: git 비ASCII 경로 octal quoting 복원(decodeGitPath — 기존 guard 것은 byte 단위 fromCharCode라 UTF-8 복원이 아니어서 새로 정확 구현), 미추적 신규 디렉터리 접힘(`?? src/`)으로 매핑이 빗나가던 것(`--untracked-files=all`). 둘 다 정산 스코프 계산의 입력 문제라 회귀로 고정.
