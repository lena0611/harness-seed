# /기획문서연동

기획팀이 관리하는 문서 저장소를 이 프로젝트의 개발 기준으로 연결합니다.

기획팀은 코드도 하네스도 모릅니다. **연결과 매핑은 전부 이쪽(개발 저장소)이 소유**합니다. 기획 저장소에는 아무것도 쓰지 않습니다.

인자: `$ARGUMENTS` — 저장소 주소가 함께 오면(예: `/기획문서연동 https://...git`) 질문 없이 그 주소로 바로 2번을 진행합니다.

## 0. 개념: 도장, 캐시, 정산

- **기준 시점(lock)** — "우리 팀은 이 시점 기획을 기준으로 개발한다"는 도장. `.harness/spec-lock.json`으로 커밋되어 팀 전체가 공유합니다.
- **캐시** — 기획 문서 본문. 각자 로컬 전용이며 git이 추적하지 않습니다.
- **정산(settle)** — "이 기획 변경을 살펴봤다"는 선언. **자기 몫(자기 변경 코드에 매핑된 문서)만** 도장을 전진시킵니다. 남의 영역 문서를 함께 전진시키면 그 팀이 봐야 할 변경 신호가 사라집니다.

명령은 역할이 다릅니다. 혼동하면 팀 기준이 사고로 움직입니다.

```bash
npm run harness:spec:fetch                # 팀 기준 이동 — 최초 연동, 의도적 전체 이동에만
npm run harness:spec:fetch -- --cache-only # 최신 기획을 캐시로만 (기준 불변, 변경 목록 확인)
npm run harness:spec:fetch -- --at-lock    # 팀 기준 시점 그대로 본문 수화 (새 노트북, 신규 합류)
npm run harness:spec:settle                # push 대기 변경에 매핑된 문서만 정산 (--doc <경로> 명시 가능)
npm run harness:spec:status                # 오프라인 상태 확인 (기준 대비 미정산 목록)
```

## 1. 연결 상태 확인

```bash
npm run harness:spec:status
```

- 연결이 없으면 → 2번(최초 연결)으로 갑니다.
- **이미 연결되어 있으면 → 업데이트 흐름으로 갑니다**:

```bash
npm run harness:spec:fetch -- --cache-only
```

  1. 기준 이동 없이 최신 기획을 받고, 변경/추가/삭제 문서 목록을 확인합니다.
  2. **변경된 문서(이 개발자 담당 영역)**: 매핑된 코드가 새 사양과 어긋나는지 확인하고, 필요한 반영 작업을 보고합니다(구현은 승인 후). 확인이 끝난 문서만 `npm run harness:spec:settle -- --doc <경로>`로 정산합니다. 코드 반영 없이 영향이 없다고 판정하면 근거를 decision-log에 남기고 정산합니다.
  3. **담당 밖 변경 문서**: 대신 판정하지 않습니다(코드 맥락 없는 판정은 잘못된 매핑만큼 위험합니다). `developer-input-queue.md`에 "기획 변경 확인 필요: <문서> → <담당>" 항목을 등록하고, 해당 담당에게 전달하도록 개발자에게 안내합니다. 담당은 spec-map 비고 컬럼을 참고합니다.
  4. **추가된 문서**: 3번(매핑 만들기) 방식으로 매핑 후보를 제안합니다. 아직 미구현 사양이면 미매핑으로 남기고 그렇게 보고합니다.
  5. **삭제된 문서**(기획이 archive로 옮긴 것): `spec-map.md`에서 해당 행을 정리하고, 연결돼 있던 코드가 폐기 대상인지 개발자에게 확인한 뒤 `spec:settle -- --doc <경로>`로 기준에서도 정리합니다.
  6. 변경이 없으면 "기준 시점 최신, 매핑 N건 유지"로 짧게 보고하고 끝냅니다.

## 2. 저장소 연결 (최초 1회)

**아직 연결이 없고 인자로 주소도 받지 않았다면, 다른 설명 없이 곧바로 저장소 주소부터 묻습니다** — 이 스킬의 첫 응답은 질문이어야 합니다.

> 기획 문서 저장소 주소를 알려주세요.

주소를 추정하거나 후보를 제시하지 않습니다. 개발자가 입력한 주소를 그대로 사용합니다.

`.harness/spec-sources.json`을 만듭니다. 없으면 새로 만들고, 있으면 소스를 추가합니다.

```json
{
  "version": 1,
  "sources": [
    {
      "id": "planning",
      "repo": "<받은 주소>",
      "ref": "master",
      "include": ["**/*.md"],
      "exclude": ["**/README.md", "example/**", "archive/**"]
    }
  ]
}
```

- `exclude` 기본값 근거: 폴더 안내용 README, 작성 견본(`example/`), 폐기 문서(`archive/`)는 현재 사양이 아닙니다.
- 브랜치가 `master`가 아니면 개발자에게 확인합니다.

이어서 가져옵니다. 최초 연동의 fetch는 팀 기준을 만드는 의도적 행위입니다.

```bash
npm run harness:spec:fetch
```

실패하면 원인을 그대로 보고합니다. 대개 저장소 주소 오타, 브랜치 이름 불일치, git 읽기 권한 중 하나입니다. 추측으로 다른 주소를 시도하지 않습니다.

## 3. 매핑 만들기 (이 스킬의 핵심)

가져온 기획 문서는 `.harness/generated/spec-cache/<source-id>/`에 있습니다. 이 캐시는 git 추적 대상이 아닙니다.

1. 캐시의 기획 문서 목록을 읽고, 각 문서의 첫 문단으로 무엇에 대한 사양인지 파악합니다.
2. 이 저장소의 코드 구조를 확인합니다(`src/views/`, `src/apis/`, 라우터 정의 등).
3. **문서와 코드를 대조해 매핑 초안을 제안합니다.** 근거를 함께 제시합니다.

```text
features/사이트전환.md → src/views/SiteSwitch.vue, src/store/site.js
근거: 문서의 "상단 사이트 이름을 눌러 목록" 흐름이 SiteSwitch.vue의 드롭다운과 일치하고,
현재 사이트 상태를 site.js가 보관합니다.
```

4. **확신이 없는 것은 추측으로 채우지 않습니다.** 후보를 제시하고 개발자에게 확인하거나, 비워 두고 미매핑으로 남깁니다. 잘못된 매핑은 없는 매핑보다 나쁩니다.
5. 개발자가 확인한 것만 `.harness/project/spec-map.md` 표에 기록합니다. 비고 컬럼에 담당(팀/사람)을 적어 두면 담당 밖 변경의 전달이 빨라집니다.

## 4. 결과 보고

- 연결한 저장소와 기준 commit
- 기획 문서 N건 중 매핑 M건, 미매핑 문서 목록
- 매핑 없는 기능 코드 영역(있으면) — 사양 없이 구현된 곳일 수 있습니다
- 개발자 확인이 필요해 보류한 항목

**프로젝트 헌장이 아직 TBD라면** 마지막에 제안합니다: 기획 문서를 근거로 헌장 초안(문제·사용자·비목표·성공 기준)을 만들 수 있다고 안내하고, 원하면 `bootstrap.md`의 인터뷰 절차로 진행합니다 — 기획 문서에서 초안을 만들어 확인받는 방식이라 빈칸 인터뷰보다 짧습니다. **이미 채워진 헌장은 건드리지 않습니다** — 재검토는 개발자가 "프로젝트 방향이 바뀌었다"고 명시할 때만 합니다(bootstrap.md 규칙).

## 5. push 정산 게이트 (선택 — specEnforcement)

`.harness/policy/profile.json`의 `specEnforcement`로 집행 등급을 정합니다.

- `"advisory"`(기본): 커밋 검증에서 참고 정보만 표시합니다. push는 막지 않습니다.
- `"gate"`(옵트인): push 시 훅이 최신 기획을 캐시로만 받아, **이번 push 범위 코드에 매핑된 문서**가 기준 시점 이후 달라졌으면 push를 중단합니다. 게이트 출력의 정산 절차를 따릅니다: 문서 확인 → 코드 반영 또는 영향 없음 근거(decision-log) → `harness:spec:settle` → lock 변경 커밋 → 재푸시.

게이트의 성질:

- **내 몫만 봅니다.** 남의 영역 기획 변경은 그 팀의 push에서 걸립니다.
- **fail-open**: 기획 저장소를 못 읽으면 push를 막지 않고 한 줄 안내만 남깁니다. 차단 사유는 오직 "내 범위 문서의 실제 어긋남"뿐입니다.
- 미연동 프로젝트에서는 게이트가 실행 자체를 하지 않습니다.
- 비상 우회는 `HARNESS_SPEC_GATE=off git push` — 사유를 decision-log에 남깁니다.

## 6. CI 백스톱 (선택)

push 훅이 못 보는 두 가지 — 서버에서 일어나는 MR 머지, 아직 아무 코드에도 매핑되지 않은 **신규 기획 문서** — 는 스케줄 CI가 맡습니다. 기획자가 노티를 깜빡해도 이 잡이 안전망이 됩니다.

```yaml
# .gitlab-ci.yml — 스케줄 파이프라인(예: 매일 아침)으로 등록
spec-freshness:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
  script:
    - npm ci
    - npm run harness:spec:fetch -- --cache-only
    - npm run harness:spec:status | tee spec-status.txt
    # 미정산/미매핑이 있으면 매터모스트 incoming webhook으로 알림 (URL은 CI 변수로)
    - if grep -q "감지된 변화" spec-status.txt; then
        curl -s -X POST -H 'Content-Type: application/json'
          -d "{\"text\":\"[기획문서연동] 미정산 기획 변경이 있습니다.\n$(grep -A20 '감지된 변화' spec-status.txt | head -15)\"}"
          "$MATTERMOST_WEBHOOK_URL";
      fi
  allow_failure: true
```

CI 워크스페이스는 버려지므로 이 잡이 캐시를 갱신해도 팀 기준에는 아무 영향이 없습니다.

## 기준

- 기획 저장소는 **읽기 전용**입니다. clone/fetch만 하고 어떤 경우에도 쓰지 않습니다.
- 기획 문서 본문을 이 저장소에 복사하지 않습니다. 캐시와 lock만 사용합니다.
- `.harness/spec-lock.json`은 **커밋합니다.** "우리 팀이 어느 시점 기획을 기준으로 개발했는가"를 공유하는 기록입니다.
- **fetch(무옵션)는 팀 기준 이동입니다.** 최초 연동과 의도적 전체 이동에만 사용하고, 본문이 필요할 뿐이면 `--at-lock`(기준 시점) 또는 `--cache-only`(최신 확인)를 사용합니다.
- **정산은 자기 몫만.** 자기 변경 코드에 매핑된 문서만 전진시키고, 남의 영역 문서의 도장을 대신 옮기지 않습니다.
- 기획 저장소에 push된 문서는 **발효된 사양**으로 간주합니다. 기획 문서와 코드가 다르면 기본 판정은 **코드 drift**입니다. 기획 문서를 고쳐야 한다고 판단되면 직접 고치지 말고 개발자에게 보고해 기획팀과 논의하게 합니다.
- 매핑이나 연동으로 확정한 판단, 영향 없음 정산의 근거는 `.harness/session/decision-log.md`에 남깁니다.
