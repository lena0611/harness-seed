# /하네스업데이트

> **매 실행 시 이 문서를 처음부터 끝까지 다시 읽으세요.** 이 문서는 하네스 업데이트로 함께
> 바뀝니다 — "지난 세션에서 봤다"는 기억으로 절차를 건너뛰면 새로 추가된 단계(예: 결과 리포트)를
> 놓칩니다(2026-09-01 실측). 업데이트 출력도 grep 필터 없이 끝까지 확인하세요.


하네스 업데이트를 바로 실행하지 않고, 먼저 현재 설치 상태와 업데이트 대상을 분리해 확인합니다.

## 1. 먼저 후보 확인

```bash
.harness/bin/harness outdated
```

출력에서 `baseHarness`와 `stackHarness`를 각각 확인합니다.

- **outdated 출력이 안내하는 명령이 정상 경로입니다.** outdated는 설치 상태(base source가 git인지 bundled인지, 스택 유무)에 맞는 실행 가능한 명령만 안내하도록 설계되어 있습니다. 안내와 아래 표가 다르면 안내를 따릅니다.
- base source가 bundled로 기록된 프로젝트는 `--base-only` 대신 최신 스택 하네스 `npx ... init` 재실행이 안내됩니다. 이것이 정상입니다(스택 하네스가 필요한 공통 하네스를 내부 설치/업데이트).
- 둘 다 outdated이면 base와 stack의 update command를 확인하고, 필요한 순서를 사용자에게 설명합니다.

## 2. 업데이트 명령 선택

| 상황 | 명령 |
| --- | --- |
| 스택+공통 함께(기본) | `.harness/bin/harness update` |
| 공통 하네스만 | `.harness/bin/harness update --base-only` |
| 스택 하네스만 | `.harness/bin/harness update --stack-only` |
| 공통만 재확인 | `.harness/bin/harness outdated --base-only` |
| 스택만 재확인 | `.harness/bin/harness outdated --stack-only` |

- `.harness/bin/harness update` 기본 동작은 스택과 공통 하네스를 **같은 SemVer 호환 범위에서 함께** 갱신합니다(스택만 올리고 base를 outdated로 남기지 않기 위해). 한쪽만 올릴 때만 `--base-only`/`--stack-only`를 명시합니다.
- 호환 범위 밖(메이저/캐럿 초과) 업데이트는 자동 적용되지 않습니다. 후보가 범위 밖이면 추측으로 올리지 말고 영향(기준 해석 변화, 빌드 환경)을 요약해 사용자 확인을 받습니다.

## 3. 업데이트 후 확인

```bash
.harness/bin/harness changelog
.harness/bin/harness stack:status
.harness/bin/harness check
.harness/bin/harness outdated
```

확인할 항목:

- `harness:changelog`로 이전→새 버전 구간의 변경 요약을 읽고, **사용자에게 "무엇이 달라지는지"를 요약 보고**합니다(출력 형식 변화, 새 검사, 새 관례 등 작업 방식에 영향을 주는 항목 위주).
- 설치 리포트의 보존/백업 항목: 로컬 수정된 managed 파일이 보존됐는지, `.harness-bak` 백업이 생겼는지 확인하고 있으면 보고합니다.
- 공통 하네스 버전이 의도치 않게 낮아지지 않았는가? 스택의 `baseHarness.minVersion`을 만족하는가?
- `harness:check`가 통과하는가? (업데이트로 새로 생긴 경고는 숨어 있던 문제가 드러난 것일 수 있으니 changelog와 대조)
- `harness:outdated` 재실행으로 up-to-date 상태를 확인합니다.

## 4. 기록

업데이트로 기준 해석이나 프로젝트 룰이 바뀌었으면 `.harness/session/decision-log.md`에 남깁니다.

업데이트 중 외부 권한, 토큰, GitLab 설정처럼 에이전트가 처리할 수 없는 항목이 있으면 `.harness/session/manual-actions.md`에 남깁니다.


## 마무리 — 결과 리포트 등록 (0.2.136)

업데이트(또는 최초 설치)가 끝나면 결과를 본체 이슈보드에 남깁니다.

**⚠ 조용히 끝내지 마세요.** 완료 직후 사용자에게 **명시적으로 질문**해 답을 받습니다 —
Claude 계열은 질문 UI(AskUserQuestion)로: **"결과 리포트를 남길까요?"** (선택지: 등록 / 파일로만 / 생략).
답을 받기 전에 턴을 끝내지 않습니다. 건너뛰면 다음 커밋 검사가 "리포트가 아직 안 남았다"고
계속 상기합니다(생략을 택했다면 안내에 나오는 표식 파일을 지워 멈춥니다). 본체가 개선요청을 자동으로
발견하고, 배포 현황(누가 언제 어떤 버전)을 운영 관점에서 볼 수 있게 하는 장치입니다.

1. 리포트 초안을 만듭니다 — 아래 양식을 따릅니다(제목·결과 표는 스크립트가 자동으로 붙이므로
   초안은 "전달 사항"만 씁니다). 발견한 게 없으면 첫 줄만 남깁니다.

   ```markdown
   요약: 정상 완료 / 문제 N건 / 개선 의견 N건 중 택일 또는 조합

   ### ① <문제·의견 제목> — 심각도: 높음|중간|낮음
   - 증상: 실제로 본 출력·현상 (붙여넣기)
   - 재현: 밟은 경로를 순서대로
   - 원인: 알아냈으면 파일·코드 위치까지 (모르면 생략 — 추측 금지)
   - 제안: 원하는 방향 (없으면 생략)

   ### 잘 맞았던 것 (선택)
   - 개선 요청만 나열하면 균형이 안 맞을 때 한두 줄
   ```

   원칙: **증상과 재현은 필수, 나머지는 선택.** 추측으로 원인을 단정하지 않고,
   실제 출력을 붙여넣는 것이 가장 좋은 근거입니다(지금까지 반영된 요청서들의 공통점).
2. **리더에게 초안을 보여주고 승인을 받습니다** (자동 등록 금지 — 리더 명의로 나가는 보고입니다).
3. 승인되면 등록합니다:
   `.harness/bin/harness report:install -- --kind update --from <이전버전> --to <새버전> --notes-file <초안.md>`
4. 토큰이 없으면 자동으로 파일로만 남고 전달 안내가 나옵니다 — 그 파일을 리더가 본체 팀에
   전달하면 됩니다. 토큰(공용 1개)은 **하네스 본체 개발자에게 DM으로 요청**해 받아 `~/.config/ai-standard/report.env`에
   `HARNESS_BODY_ISSUE_TOKEN=<값>` 한 줄로 **개발자당 1회**만 두면 모든 프로젝트에서 동작합니다
   (프로젝트 루트 `.issue-adapter.env`가 있으면 그쪽이 우선). 토큰 값은 채팅에 붙여넣지 않습니다.
5. 보조 경로: GitLab MCP가 연결된 환경이면 `report:install -- ... --dry-run` 출력(제목·본문·이력 행)을
   **그대로** MCP로 등록해도 됩니다 — 형식은 스크립트 출력을 따르고, 이력 표 이슈(라벨 설치이력표)에
   행 추가까지 같이 합니다. 이 경우 이슈가 그 개발자 개인 명의로 등록된다는 점만 리더에게 알립니다.

발견한 문제가 없어도 "정상 완료" 리포트를 남깁니다 — 이력 표의 한 줄이 됩니다.
